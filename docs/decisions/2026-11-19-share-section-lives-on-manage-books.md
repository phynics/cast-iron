# The share section lives on Manage books, 2026-11-19

Replaces two bullets of "Book share codes, 2026-11-16" (`Where it lives` and `The link is`). The rest of that entry stands. The page is `views/share_set.rs`, inside `views/active_books.rs`.

- **The section moved from Books to Manage books** (#504). A code changes the active set as a preset does, so it belongs where the set is changed. Books keeps the count line, the `Manage books ›` link and then the first group. The section sits after the presets and before the book groups. The 2026-11-16 decision put it on Books because a code is something a reader shares from the page they read; on a phone the section pushed the book list down (the owner's iPhone screenshot, 2026-11-19), and sharing and entering a code change the active set, which is Manage books's job.
- **The canonical link is `#/books/manage?set=<code>`** (`Route::BooksSet`, `Route::href`). The link that earlier releases copied, `#/books?set=<code>`, still parses to the same route, and `read_location_route` rewrites its address to the canonical one with `replaceState`, keeping the history state. A pasted link of either form is read by the code field. The route is normalized to `BooksManage` for the shell, so answering (which replaces the address with `#/books/manage`) does not rebuild the page and drop the Undo line. The question takes the focus when a link opens it; the H1 takes it otherwise.
- **An Undo belongs to the selection revision that its change produced.** Each status line (`Applied …`, `Now using 27 books.`, `Restored your earlier choice.`) and its Undo are shown only while `Library::selection_revision` equals the revision after that change, so any later change that succeeds ends every Undo line on the page without a counter or a callback between the presets and the share section. Undo itself runs through `Library::apply_active_plan_at(revision, …)`, which checks the revision once the write holds the slot, after every earlier write has landed. An Undo that was clicked while another change was saving therefore finds a newer revision and writes nothing. Reason: an Undo that captured its inverse before the other change landed would put back books that the newer change had chosen. A write that fails does not move the revision, so it leaves the line and its Undo alone; nothing clears an Undo before the write that replaces it has succeeded. This also fixes the same race between two presets, which existed before the move.
- **A link's question belongs to the history entry that holds the link, and a save belongs to the review it answered.** Back and Forward change the entry without changing the page, and the address of the entry before a link is the address that the link is rewritten to, so the route cannot say that the reader left. The entry carries a mark in its history state (`shareLink`, a number drawn once for the entry); leaving it by Back or Forward closes the question and any error the link raised. Forward to the entry asks again while its address still carries the code. The entry that Quick search pushes on top of it is the same page with a layer over it: it is not leaving, and it is not the link's entry either. `push_flagged_entry` copies only the scroll id into it, never the mark, so a save that finishes while Quick search is open finds an entry without the mark and rewrites nothing there. The section counts its reviews (a new code, a cancel, an answer, leaving the entry). A save closes the question, or reports its failure, only while the review it began under is still the current one, so a late save of code A cannot clear the question or the text of code B that the reader reviewed meanwhile, and a failed save of A does not put its notice next to B. The books are saved either way and the status line with its Undo follows the books. When a save finishes while the reader is on another entry (Quick search's), the question closes and the link's address is rewritten when the reader is back on the link's entry. A save that finishes after the page was left updates nothing. The section holds no `Callback` for the rest of the page, because `Callback::run` panics once the view that made it is disposed.
- **Done reads the entry it leaves, not the page it was built for.** The `Manage books ›` link on Books marks the entry that it pushes (`openedFromBooks`). The link handles a plain click itself: it pushes the entry with the mark already in its history state. A click that asks for another tab, window or download (Ctrl, Cmd, Shift, Alt, the middle button) is left to the browser; it pushes nothing in this tab and so marks nothing. An earlier version raised a flag on every click and the next Manage books page that mounted consumed it, so a Ctrl-click that stayed on Books marked the entry that Settings pushed later, and Done there went Back to Settings. Done goes Back only when the entry on screen carries the mark; any other entry, such as one that a share link pushed on the same page or one that Settings pushed, is replaced with Books. Focus returns to the Books link in both cases. The mark survives Back, Forward and a reload, so after a reload on the first entry Done still returns to Books.
