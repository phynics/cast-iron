# Local diagnostics for the iPhone measurement session, 2026-11-17

Refs [#423](https://github.com/phynics/cast-iron/issues/423) and [#419](https://github.com/phynics/cast-iron/issues/419). The owner's checklist is `docs/research/iphone-measurement.md`; the code is `crates/web/src/diagnostics.rs` (model, summaries, text) and `views/diagnostics.rs` (the page).

- **The app records its own timings and shows them at `#/settings/diagnostics`** (`Route::Diagnostics`, linked from Settings under "This app"; Settings stays highlighted). The owner has an iPhone and no Mac, so Web Inspector is not an option. The page is the report: its sections are plain text, and Copy puts exactly that text on the clipboard. Nothing is sent anywhere (rule 1); a Playwright test checks that Refresh and Copy make no request.
- **The marks are always on; the page probe is not.** The marks and the search samples are a few `performance.now()` calls and a bounded in-memory append (at most 60 searches and 12 pages per launch). The store is one IndexedDB `meta` record (`diagnostics`: the last 8 launches and the last install), written when Home first paints, when the search index is ready, when Diagnostics is opened or refreshed, and after an install. A write that fails is ignored. `DB_VERSION` does not change; an older or newer shape reads with defaults. Counting a page's elements and copying its text is more work, so it runs only for pages opened after the Diagnostics screen was first opened in the launch (`start_page_probe`). The checklist opens Diagnostics first in each launch that measures pages.
- **The record is written in one transaction.** `store::update_meta` reads, changes and writes the `diagnostics` record inside one IndexedDB transaction, so two tabs cannot take the same launch number or overwrite one another. A per-tab lock keeps one tab's own writes in order. A record that no longer decodes counts as missing.
- **Clear diagnostics removes this record and nothing else** (`diagnostics::clear`): the stored launches and install, and what the current launch measured. Its start time, display mode and first screen stay. Refresh stores the launch again. Reason: the data is bounded and local, but clearing all website data would also remove the library and the stars.
- **The privacy statement covers this report.** The report holds counts, lengths, times and the titles of public entries, never query text. The recent searches that Quick search lists are stored separately and do hold query text.
- **What is not kept.** The text of a query never leaves the search screen: a sample holds the length, the result count and the times. Page samples hold the entry title, which is public rule text.
- **No new JavaScript.** Copy is `js::copy_text` (#408). The WebAssembly memory size is `wasm_bindgen::memory()`. `performance.memory` is read by reflection and only exists in Chromium. The clock is `performance.now()`.
- **Safari gives a web page no memory number.** `performance.memory` and `measureUserAgentSpecificMemory` are absent, and the text says "not offered by this browser". The iPhone session therefore measures what the app can see: the WebAssembly linear memory that was allocated (a high-water mark, since it never shrinks; not live objects and not the process total) and the element and text size of the page. For the real question it checks for a suspected restart: a higher launch number proves only that the page started again, and the owner records what happened just before. A Mac with Web Inspector is needed only if that check shows a problem.
- **A cold start is counted from the start of the page.** The marks are app code running, library files checked (`check_installed`, a presence check of every manifest file, so its cost grows with the file count, which matters for format 5), catalog read, library ready, and Home painted two animation frames after it mounted. The time that iOS needs to open the web view before the page starts is not visible to the app; the owner counts it by hand. Home's time is recorded only when the launch opened on Home.
- **Search time runs from the start of the run to the painted results, on both screens.** The full results page and the Quick search suggestions each record a run: "work" ends when the results are handed to the screen, "total" ends two animation frames later, and a run that a newer one replaced is dropped. The typing pause before a run (`views::search::DEBOUNCE_MS` 80 ms, `quick_search::SUGGEST_DEBOUNCE_MS` 100 ms, both `pub`) is stated in the text and not counted. "Total" includes waiting for the index, which is about zero after Home loaded it in the background. The first search is reported apart from the rest; "typical" is the nearest-rank median (the lower middle of an even count) and 95th percentile of the others, and with under 20 later searches the 95th percentile is the slowest.
- **Install time has four phases** (scan, download, verify, activate) and the answer that `navigator.storage.persist()` gave. A resumed install shows the files that were already there, and the download rate counts only the bytes fetched (none, when every file was there), so a restart does not read as a fast download. Only a finished install is recorded.
- **The eviction check records an observation, not a cause.** The checklist's seven-day wording follows WebKit: seven days of Safari use without interacting with the site (not calendar days), a Home Screen exemption that covers that rule only, and eviction under storage pressure as a separate cause ([Full Third-Party Cookie Blocking and More](https://webkit.org/blog/10218/full-third-party-cookie-blocking-and-more/), [Tracking Prevention in WebKit](https://webkit.org/tracking-prevention/), [Updates to Storage Policy](https://webkit.org/blog/14403/updates-to-storage-policy/)). The owner writes down the days of Safari use, whether the site was touched, and how full the phone is, and reports kept or cleared without naming a cause.
