# Book share codes, 2026-11-16

Closes [#408](https://github.com/phynics/cast-iron/issues/408) when its acceptance passes. Builds on "Book presets and third-party books, 2026-11-06" and "Active books and the presets, 2026-11-07". The code is `crates/web/src/book_code.rs` (the format) and `book_share.rs` (a code against a catalog); the page is `views/share_set.rs`.

- **A code names slots, not ids and not catalog order.** A book's slot is its line number among the id lines of `sources/published-books.txt`, an append-only file in this repository. `cargo xtask content` passes it to the compiler (`--book-slots`), which gives every catalog source `SourceInfo.share_slot` and fails, naming each book, when a source has no line. Reason: stability across corpus updates is the hard requirement. A corpus bump that adds, removes or reorders books cannot change the slot of any other book, because slots never come from the corpus.
- **The file lives here, not in the corpus.** The corpus needs no change and no new pin, so the feature ships as one PR. A corpus bump that adds a publication fails `cargo xtask content` until `cargo xtask published-books` appends the new ids (oldest first, undated last, ties by id) and the PR commits the lines. The command reads `publications.toml` from the verified cache, so it works while the compiler is failing.
- **Permanence is enforced by comparison with history, not by the file.** `sources/published-ids.txt` is guarded by what it must resolve to, which a sorted set can check without history. An ordered list cannot: the compiler sees only the file it is given, so a reorder, a replaced id or a deleted line would build and silently change what every shared code means. `cargo xtask check-book-slots [--base REF]` takes the file at `REF` (default `origin/main`) and fails unless every id line of that version is at the same position in the working file; only appends pass, and the change that introduces the file passes because its base has none. CI runs it on every pull request against the base commit (`github.event.pull_request.base.sha`, fetched on its own, step "Book slots only grow"), and `cargo xtask check` runs it against `origin/main` when that ref exists, so a local check catches the edit before the push. Only a base tree that lacks the file passes (`git ls-tree` says so); a bad ref, a missing commit or any other git failure fails with git's message. Tests cover a valid append, a reorder, a replacement, a deletion in the middle, at the end and of everything. Not covered: a direct push to `main`, which skips review and CI alike. A baseline committed beside the file was rejected: an edit of the file could edit its baseline in the same commit. Never edit, move or delete a line.
- **A book that leaves the library keeps its line.** The build does not fail for it: a takedown must stay possible (rule 10). A code that turns that slot on is skipped on the receiver and counted. A renamed book id is a new book with a new slot; old codes then skip it. Book ids are already permanent (routes, `disabled_books`), so a rename is not expected.
- **The first 439 lines are in Books order** (tier, then oldest first, ties by title; third-party last). A preset is then a block of neighbouring slots, so its code is short. Later books are appended in publication order, so a new Rulebook is not next to the first block and costs one more run in a preset's code. The order is a one-time seed; nothing depends on tiers after that.
- **`SourceInfo.share_slot` is additive, so `SCHEMA_VERSION` and `INDEX_FORMAT_VERSION` stay.** Like `category` and `third_party`, an older catalog has no field and an older reader ignores it. It changes `catalog.json` for the next library, which is true of any corpus change. A reader that finds a source without a slot (a library compiled before this change) hides the share controls instead of guessing. This does not join "format 5".
- **The code is a version, a payload and a check character in Crockford base32** (`0-9 A-Z` without I, L, O, U). The first character is the format version (`1`). The last is a check: the sum of `(value + 1) * 3^i` over the earlier characters, modulo 32. All weights are odd, so any single wrong character is caught (tested for every position and every replacement), two swapped neighbours are caught unless their values differ by exactly 16 (tested), and a missing or extra character is caught in about 31 of 32 cases. One character is what the issue asked for; two would catch more and cost a character on every code. The check covers the version, so a typo in the version is a typo and not a "newer version". A correct check with a version this app does not read says `This code comes from a newer version of Cast Iron`. The envelope stays the same in later versions for that reason.
- **The payload says which slots were on, and how many slots the sender knew (`described`).** Its first bit picks one of two encodings, and the writer takes the shorter. Runs: Elias-gamma lengths of alternating off and on runs, off first, adding up to `described`. Bits: gamma of `described + 1`, then one bit per slot. Zero bits pad the last character; a decoder rejects a stream that does not end in less than five zero bits. The format is written out in the module doc of `book_code.rs` and again, independently, in `tests/e2e/tests/books-share.spec.ts`.
- **A book the code does not describe keeps its state.** A slot at or above `described` is a book the sender's library did not have. Applying the code leaves it alone: a code made last month does not turn off a book that arrived since. An on-slot that this library has no book for is skipped, counted, and reported (`2 books in this code are not in your library, so they are skipped`). Everything else is set exactly, so on a library with the same books the active set matches the sender's. Reason: both directions of library drift (receiver older, receiver newer) must do the least surprising thing.
- **Typical lengths, for the 439 books of corpus v0.1.21** (version and check included; the four presets are read from the built app, the other sets are the same encoder run on generated sets): Paizo Everything 7, Everything incl. 3rd party 6, Paizo Rulebooks 8, Paizo Rulebooks & More 9, a preset with one book changed 10, Rulebooks plus 3 to 10 adventures 14 to 26, a custom set of 20 books chosen across the library 38, 50 books 61, and at worst about 94 characters (an alternating set), which is the cost of one bit per slot. The app shows groups of four joined by hyphens (`1AB2-C3D4`); readers ignore case, spaces, hyphens, `I` and `L` (read as `1`) and `O` (read as `0`). The Enter field also accepts a pasted share link.
- **The delta-from-preset option is not used.** A preset is a rule over tier and the third-party flag, so a book that a later corpus adds, or reclassifies, would change what "Paizo Rulebooks plus these" means. A code over slots depends on nothing a corpus update can change.
- **The link is `#/books?set=<code>`** (`Route::BooksSet`). It opens Books and asks; it never applies. The route is normalized to Books for the shell, so answering (which replaces the address with `#/books`) does not rebuild the page and drop the Undo line. A bad link says why, applies nothing, and clears the address. Opening the link and reloading asks again; only an answer clears it. A bad link says why (`This link's code does not look right. …`) in an alert outside the disclosure (which is closed when a link opens the page), so the reader never lands on plain Books with no explanation.
- **Applying goes through `Library::apply_active_plan`**, so the change is worked out after any earlier write has landed, like a preset. Undo is the inverse change. It lasts until another selection change succeeds: reviewing a code, a rejected typo and a cancelled question leave it alone, because no book changed. The result line is the Books count line (`28 of 439 books active · Paizo Rulebooks`, or `Custom`), computed for the state after the change, so a code that equals a preset names it.
- **Where it lives.** Books, not Manage books: the issue asks for the Books page, and a code is something a reader shares from the page they read. It is a collapsed disclosure under the head so the directory stays first. The question opens above it and takes focus, so a link or a typed code lands on it at 390 px.
- **The decoder bounds its input before it allocates.** A valid code has at most 1,244 characters (`MAX_CODE_CHARS`: bit mode needs about 4,122 payload bits, run mode at worst 3 bits per 2 slots, about 6,146). Normalization stops at that length, before it stores or unpacks a character, and answers `This code does not look right` for a longer text whatever its check says. Reason: a pasted code or a hash link is untrusted, and the 4,096-slot limit applies only after the payload is expanded. Tests cover an input one character over the limit with a correct and with a wrong check, a million characters, separators (which do not count), and the longest valid code.
- **No new JavaScript.** Copy calls `navigator.clipboard.writeText` from Rust by reflection (`js::copy_text`), not through `bridge.js` and not through an unstable `web-sys` API. Where the clipboard is missing or refused, the page says so and the code block selects whole on a tap. Nothing leaves the device (rule 1); a Playwright test checks that the server sees no request while a code is reviewed, applied and undone.
- **A pin PR that adds a publication now needs one more step.** It runs `cargo xtask published-books` and commits the lines, or the content build fails and says which books lack a slot. The v0.1.22 pin ([#410](https://github.com/phynics/cast-iron/pull/410)) adds no publication, so the file needed no extra line when this change met it.
