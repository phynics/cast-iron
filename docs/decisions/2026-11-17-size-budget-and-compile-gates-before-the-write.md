# Size budget, and compile gates before the write, 2026-11-17

Refs [#426](https://github.com/phynics/cast-iron/issues/426).

- **Three measures, one file.** `sources/size-budget.toml` limits `library_bytes` (every file under `generated/content`), `largest_file_bytes` (today `search.bin`), and `wasm_bytes` (the one `*_bg.wasm` in `dist/`). Each limit is the measurement on corpus v0.1.23 plus about 5%, rounded up: library 223,140,755 to 234,300,000; largest file 68,762,988 to 72,300,000; WASM 3,123,287 to 3,280,000. The largest file has its own limit because a regression in the search index would otherwise hide inside a 5% library margin (about 11 MB). Raising a limit is a one-line change in the PR that grows the build.
- **Raw bytes, not compressed.** GitHub Pages compresses on the wire, but the installed library is the raw bytes that the service worker stores, and that is the cost to a reader's device. The WASM limit is also raw.
- **CI runs it in the site job**, after the site build and the publication screen, where `generated/` and `dist/` both exist. `pages.yml` does not repeat it: a release is a commit that CI already passed.
- **The reachability gate moved into `package`.** Before, `main.rs` wrote the library and then exited 1 when entries were unreachable, so a failed compile left a manifest on disk and a retry of `build-site` saw it and published an ungated library. `package` now returns the failure before the first write. `main.rs` only prints the search-index warnings.
- **The library is staged, then handed over in recoverable steps.** `publish_staged` (in `publish.rs`) writes `generated/content.staging`, the manifest last, renames `generated/content` to `generated/content.backup`, renames the staging directory to `generated/content`, and deletes the backup. A first version deleted the old library recursively before the rename; Sol's review of #431 showed that an interruption during that delete leaves a non-empty directory with no manifest, which the next compile rejected as foreign and could not repair. Each step now leaves a state that `recover_out` reads at the start of the next compile: a backup with no library and a whole staging directory finishes the handoff; a backup with no library and no whole staging directory restores the backup; a library that is whole, with a backup, removes the backup (the new library is live); a leftover staging directory is removed. It stops only on a foreign `generated/content` or when no whole copy is left. "Whole" is defined below; the manifest is written last, so a directory without one is partial.
- **One compile at a time, by a fail-fast lock file.** Recovery removes a staging directory and a backup, which are a live writer's files while it publishes. Without a lock, compile B could remove compile A's staging between two of A's writes; A's later writes would recreate the directory, and A would back up the good library, activate an incomplete staging directory and delete the only good copy (Sol's review of #431). `OutLock::acquire` takes `<out>.lock` with `create_new` (atomic) before the first recovery, and it is held until `package` returns, so recovery, gates, staging, the renames and the delete all run under it. `recover_out`, `publish_staged` and `package` take the lock as an argument, so no entry point can reach them without one. The file holds the pid, the start time and a nonce, and `Drop` removes it only while the file still holds that text, so a compile never removes the lock of a later one after a person deleted its own. A small window remains between the read and the unlink; it needs a person to delete a live lock, which the docs forbid. A second compile fails at once rather than waiting: a wait would hold a CI job for no result. The message names the holder and how long ago it started, says nothing was changed, and says to delete the file if no compile is running. A finished compile leaves nothing in `generated/`, so the determinism job (`diff -r`) is unaffected.
- **No automatic stale-lock removal.** A killed compile leaves its lock, and a person deletes it after checking that no compile runs (`docs/releasing.md`, "Compile gates"). The first version of this lock reclaimed a lock whose pid was gone, using the process start time from `/proc`, a retry loop and a guard file. That is more protocol than a single-owner project needs, and its first form treated an unreadable `/proc` as a dead holder, which could remove a live compile's lock. Choosing the simpler lock removes that class of error; the cost is one manual `rm` after a crash. A different design (an OS file lock on a file outside `generated/`) would also work and was not chosen, to keep the code small.
- **Recovery keeps a copy only when it is whole.** "Whole" is the installer's structural check (`validate_manifest`) plus the size and SHA-256 of every listed file, replacing a check of the manifest and sizes alone. Recovery reads this only when a backup exists, so a normal compile does not hash the library. A staging library with a wrong byte is not activated; an activated library that fails the check does not replace a good backup, which is restored; and when neither is whole both stay and the message names them.
- **What is and is not guaranteed.** For one compile at a time: a failed gate, or a write error into staging, leaves `generated/content` unchanged, and a failed first compile leaves no manifest. A killed process between the steps is repaired by the next compile. A library that was moved into the backup is never lost: it comes back, or the new one replaces it only when whole. A compile that stops after the staging library is finished but before the first rename has no backup, so that staging directory is discarded and rebuilt, not activated; the guarantee is about the previous library, not the work in progress. Between the two renames `generated/content` is absent; `build-site` then compiles again. The code never calls `fsync`, so a power loss or host crash can leave files with the right names and wrong bytes; `build-site` catches that by hashing. Renames are atomic only within one file system, and the staging and backup directories are siblings, so the usual layout satisfies that. A mount point at `generated/content` would not, and the rename would fail loudly. Windows can fail a rename or delete on an open handle; no Windows path exists in CI. The reports directory has no lock.
- **`build-site` verifies the library it uses.** It parses `manifest.json` as a `ContentManifest` and applies `validate_manifest`, then hashes every listed file. The structural check is the one the installer runs before it downloads (known schema, valid content version, safe and unique paths, valid checksums, the four required files, total equal to the sum), moved from `crates/web/src/install/plan.rs` into `cast_iron_schema::manifest_check` so the app and xtask share it; the web crate re-exports it. `{"files":[]}` fails, and so does a manifest that lost a required row together with its file. This shows the directory is the library its manifest describes. It does not show gate provenance: the compiler guarantees that by writing no manifest when a gate fails.
- **A failed compile does not delete the previous library.** The issue asks that a failed gate leave `generated/content` unchanged. A reader of a failed run's output must therefore look at the exit status, not at the directory.
- **`pages.yml` compiles outside the retry loop.** The loop exists because Trunk downloads tools from GitHub on a cold cache. A gate failure is not a download failure, so it now fails once, with its own message, and the loop repeats only the Trunk build.
