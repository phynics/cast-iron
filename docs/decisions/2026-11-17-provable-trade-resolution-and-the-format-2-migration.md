# Provable trade resolution and the corpus format 2 migration, 2026-11-17

Refs [#451](https://github.com/phynics/cast-iron/issues/451), part of [#251](https://github.com/phynics/cast-iron/issues/251). It builds on [typed trades and `trades.json`](2026-11-17-typed-trades-and-trades-json.md). Applying the step to the corpus repository is #452.

- **A trade resolves only when its printed name proves the feature.** The design pass for #251 counted 912 archetypes that "resolve every item" with scripted level and qualifier matching. That script is not in the repository. A containment rule (a name that holds all the words of one heading) reproduces a similar count (about 870 on the pinned corpus), but it also resolves `Improved evasion` to `Evasion`, `Bravery and the fighter bonus feat gained at 2nd level` to `Bonus Feats`, and `Bonus skills from the oracle's mystery` to `Mystery`. Review of #470 rejected that kind of match, because a wrong link is worse than none: a compatibility filter reads a resolved trade as exact and an unresolved one as never compatible. So the step uses four rules, each needing exactly one matching heading: exact slug, token set, ordinal levels, and one qualifier. [Corpus format: Migrating to format 2](../corpus-format.md#migrating-to-format-2) states them. The count of fully resolved archetypes is what those rules prove (see the PR for the count on corpus v0.1.25), not 912; the rest is in the review queue.
- **An ordinal is a level only inside a level expression.** `2nd favored enemy` is the second enemy a ranger picks (at 5th level), not level 2. An ordinal counts as a level only when the run it belongs to (ordinals joined by `and`) is followed by `level` or `levels`. One ordinal outside such a run, even next to a real level (`2nd favored enemy gained at 5th level`), leaves the whole trade unresolved (`ordinal-is-not-a-level`).
- **A numeric anchor proves nothing alone.** A second heading with the same text gets the anchor suffix `-2`, `-3`, so `trap-sense-3` may be a collision, not the +3 step. An anchor with a number in it matches a name only through the heading's own text; otherwise the name goes to the qualifier rule, which reads the number as `power` and needs one matching heading.
- **Anchor ownership counts every base class.** The classes that hold an anchor are taken from all base headings with that anchor, not from the headings whose text matched. Otherwise `Alchemies` could resolve to an anchor that another base class holds under another text, the compiler would reject it, and a second run would drop the feature the first run wrote.
- **A qualifier goes to `power` only when it is one number (`+4`, `2`) or a one-word parenthesis (`(minor)`).** A list of numbers (`Armor training 1, 2, 3, and 4`) cannot be one `power`, and a longer parenthesis is an editor's note (`(but see text)`, `(including extracts)`), so those stay unresolved. `power` is compared by exact text, so a wrong or noisy value would hide a conflict.
- **A feature that several base classes hold stays unresolved.** Format 2 would need a written `class`, and the printed name does not say which class. This includes a feature that the format 1 reader had resolved by name: the migration drops it, which matches the compiler's format 1 behaviour (it already leaves such a trade unresolved).
- **Two trades of one key never claim the same feature.** A first version of the step left 61 overlaps on the pinned corpus: 39 between a `replaces` and an `alters` trade, 22 between two trades of one key. Books print `Smite evil` twice and list overlapping bonus feats, and the drift check forbids dropping a printed name, so an error on them would block #452. The overlap rule therefore compares trades of one key only (an archetype may alter `Hexes` and replace its `6th-level hex`), and the step leaves the later of two competing trades unresolved (`duplicate-feature`). Two trades that cannot both be the proven reading are not proof for either. The rule is an error in format 2 and a warning in format 1.
- **The format 1 reader's links are judged again.** The reader links a printed name to an anchor of its list by slug alone, which proves less than the resolver (the numeric-suffix case above). The migration runs every format 1 feature through the resolver: the same feature stays, a better proof replaces it, and no proof leaves the trade unresolved.
- **The step never changes a trade that has a feature in format 2** (a format 1 feature is the exception when the resolver does not prove it, or when it duplicates an earlier trade). A fix from the review queue survives a second run, and a migrated corpus is a fixed point (no byte changes, same queue except the old-anchor column, which only a format 1 read can fill). The step writes the entries first and `corpus.toml` last; a corpus that holds files of both formats does not load, so an interrupted run is retried from a clean checkout.
- **Class options whose lines sit below the normal part are not typed.** The 40 class options of the pinned corpus that print `**Replaces:**` or `**Alters:**` lines are domains with subdomains (and the like): the lines belong to the variant subsection, not to the entry. The drift check reads the normal part only, so a trade on the entry would disagree with it, and a trade on the domain would claim that the domain replaces its own power. They stay out of `trades` (the open question of #251, a per-power shape) and appear in the queue as `variant-only` rows. The step does make unresolved trades from a printed line in the normal part when its key has none; on the pinned corpus that finds nothing.
- **The checks are gated by corpus format, not by the tool.** The corpus repository builds its checker from this repository's `main` and stays on format 1 until #452. A rule that the pinned corpus may break (two trades of one key on one anchor with the same levels and power) is a warning in format 1 and an error in format 2. A feature that several base classes hold with no `class` stays with the compiler, which fails on it in format 2. The count of unresolved trades is one warning in every format, and format 2 adds one warning for each unresolved trade whose printed name proves a feature. Rules that format 1 cannot break (`levels` 1 to 20, ascending, unique) are errors in both.
- **The review queue is a TSV outside the corpus.** `cargo xtask corpus-migrate-trades` writes `generated/trade-review.tsv` (ignored build output); the `cast-iron-corpus` binary refuses a `--review` path inside the corpus, because a stray file would fail the next check. #452 turns the rows into data pull requests.
