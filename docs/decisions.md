# Decisions

Decisions that refine `docs/spec.md` and that a later reader cannot derive from the code.

## The daily update check is opt-out and same-origin, 2026-11-06

Refs [#206](https://github.com/phynics/cast-iron/issues/206). Owner decision, recorded in the issue on 2026-11-06. This narrows `docs/spec.md` line 269 ("No app-initiated network requests occur during ordinary reference use"), line 279 ("Content updates are optional and explicitly initiated while online"), and AGENTS.md rule 1.

- **What is allowed.** The app may fetch its own `content/manifest.json` without a tap: same origin only, never a third-party host, and never any other file. It never downloads the library, never activates anything, and never asks for persistent storage. Downloading still needs **Download update**.
- **When.** At app start and again when the document becomes visible, but only while online and at most once every 24 hours. A start event and a visibility event cannot run at the same time: the in-flight flag is set before the fetch starts. `should_check` in `crates/web/src/updates.rs` is the rule, and its native tests pin the interval, the online gate, the switch, and a clock that moved backwards. A failed attempt counts as the day's attempt, so a flaky server is not asked on every focus.
- **On by default, opt-out.** Settings shows the switch **Check for updates automatically**, on unless the reader turns it off. The choice is stored in the IndexedDB `meta` store (`auto_update_check`); an absent value means on. The switch is the only way to stop the check, and the manual **Check now** always remains.
- **State survives a reload and works offline.** The check stores `last_checked`, the newest manifest's `content_version`, and its `total_bytes` in the `meta` store (`update_check`). After a reload or offline, the header pip and the Settings row come from that record. The manifest itself is kept only for the session: the installer panel mounts only when this session has it, because the panel fetches a manifest on mount and that would bypass the switch and the daily budget. Without it, Settings names the version and size it stored and offers **Check now**.
- **Small and silent.** The check is a background request (a few tens of KB) that no screen waits for. A failure changes nothing on screen unless the reader pressed **Check now**; the automatic path ignores it.
- **The header names what is waiting.** The update action appears for an app update or a known newer library, and opens Settings → Updates. Accessible names: "App update ready. Open Settings", "Library update available. Open Settings", and "Updates available. Open Settings" when both wait. The one-action rule still gives Update priority over Install.
- **Updates come first while something waits.** Settings renders the Updates section at the top when an app update is ready or a library update is known, and in its usual place otherwise. It shows the app row (with **Reload**) and the library row (version and size, the note "Your stars and book choices are kept.", and the installer panel) separately, then **Check now** and "Last checked: …".

## Creature CR drift covers Challenge rating lines, 2026-11-06

Refs [#198](https://github.com/phynics/cast-iron/issues/198). The checker is
`crates/corpus/src/drift.rs`.

- **A creature's `cr` field is compared with its `**Challenge rating:**` line, not only a
  stat block `CR` row.** Most creatures state the rating as the bold labelled line and have no
  fenced stat block, so 3,407 of the 3,718 creatures with a `cr` field were not compared
  before this.
- **The comparison parses the rating.** `ChallengeRating::parse` turns both sides into
  24ths, so a fraction such as `1/2` agrees with the same fraction and a changed fraction is
  reported like any other disagreement. A statement that does not parse (`variable`, a
  template adjustment) falls back to comparing the displayed text.
- **Several rating lines are ambiguous.** An entry with more than one line (the elementals,
  ettercap, some vehicle and template entries) usually has no `cr` field, so nothing is
  compared. When a field does exist, the field agrees if any of the statements does, the
  same rule a feat uses for a repeated label.

## The header update action opens Settings, 2026-11-06

Refs [#205](https://github.com/phynics/cast-iron/issues/205).

- **The header never reloads by surprise.** The Update action used to call `applyShellUpdate()` from the one tap, which reloaded the app mid-lookup with nothing on screen saying so. It now opens Settings on its Updates section, where **Reload** applies the app update and **Download** offers the library. Update still outranks Install in the one header slot.
- **The label says what is ready, the accessible name says where it goes.** The visible label is "Update ready" (the icon and pip alone below 48 rem), and the accessible name is "App update ready. Open Settings". A button that names its destination is the rule from here on.
- **The destination is `#/settings?section=updates`.** Settings has no route per section, so the query names the part of the screen to land on. `Route::parse` still returns `Route::Settings`, so links, `aria-current`, Back and the route signal are unchanged; `route::wants_updates_section` reads the query. It is shareable and survives a reload, and the destination is a normal history entry.
- **Focus moves to the section.** The Updates section carries `id="set-updates"` and `tabindex="-1"`. After a route change the Reader's effect scrolls to the top and focuses `<main>` one animation frame later, so Settings waits two frames before it scrolls the section into view and focuses it. When Settings is already the current screen the route does not change and no rebuild happens, so the action scrolls and focuses directly.
- **Reload keeps its own row and its own behaviour.** `js::apply_shell_update()` is reached only from that button.

## Two-step release, 2026-11-06

Refs [#127](https://github.com/phynics/cast-iron/issues/127). The owner approved the release and chose how the PSRD-first prep commit reaches `release`.

- **The PSRD step was a one-time fast-forward push.** `promote-release.py` refuses the prep commit (`ae032ba`, the tag `psrd-last-buildable` plus one `pages.yml` line that adds `--psrd`) because it was not on `main` at the time and has no `main` CI run for that SHA. The owner chose `git push origin ae032ba:refs/heads/release` over an exception in the helper. `release` was at `d48eaa3`, an ancestor of the prep commit, so nothing was reset or forced. The helper is unchanged, and every later promotion uses it.
- **The release history reaches `main` through an `ours` merge.** #184 merged `release` into `main` with `-s ours`, so `main`'s tree did not change and the `--psrd` line never reached `main`. That merge commit makes `release` an ancestor of `main`, so the canonical promotion (`ccbfb7c`) was a normal fast-forward with the helper.
- **The owner's hand check before the canonical step was done by the agent alone.** On 2026-11-06 the owner chose "agent checks, then promotes": a local walk of the corpus-built app and a Chromium e2e sample on `ccbfb7c`, then promotion without waiting for the owner. Physical devices (#12) remain open.

## Drift between typed fields and body text is an error, 2026-11-06

Refs [#180](https://github.com/phynics/cast-iron/issues/180). The checker is
`crates/corpus/src/drift.rs`; `corpus-check` runs it.

- **A disagreement fails the check.** `corpus-check` and `cargo xtask content` exit non-zero and
  list every disagreement, so a value cannot disagree in `[fields]` and the body without failing
  the build. The pinned corpus `v0.1.2` has 0 disagreements.
- **The report stays available.** `--drift-report FILE` still writes the count per kind and one
  line per disagreement, whether the check passes or fails. It no longer needs a warning to pass:
  drift was a warning only while the freeze data still held disagreements.

## Plain-text corpus, step 1, 2026-11-06

Refs [#127](https://github.com/phynics/cast-iron/issues/127). The corpus becomes the hand-edited source of truth in a public data repository, and upstream is never re-imported. Two design reviews shaped the format below.

- **The corpus is one Markdown file per entry and a few TOML source files.** Entry paths come from the permanent `ref/` id, so `ref/spell/fog-cloud` is `entries/spell/fog-cloud.md`. `corpus.toml` (format version and defaults), `publications.toml`, `books.toml`, `legal.toml`, `exclusions.toml`, `history.toml`, and `aliases.toml` hold the rest. The format is specified in `docs/corpus-format.md`.
- **Derive before storing, except what the import decided.** `relations.json`, `lists.json`, `backlinks.json` and its shards, `search.bin`, the manifest, catalogue stubs, `entry_count`, and every coverage count are compiler output. A frozen coverage file went stale on the first edit, so the stored part is only `exclusions.toml` (excluded paths and rejected records with reasons, append-only) and `history.toml` (the upstream digest, upstream record counts, how prerequisite wording was read, parts left unplaced, how page numbers placed entries in books; never edited). The round trip rebuilds the whole coverage report from the entries and those two files and requires it to equal `coverage.json`.
- **Text is for people.** Paragraphs wrap at about 100 columns; Enter is a space, a blank line is a new block, and a trailing backslash is a line break. A reader trims blanks around every line, heading, and table cell, so a wrapped and an unwrapped paragraph mean the same. `\0` and `\e` are gone: the writer merges adjacent text and drops empty text, and the canonical compile does the same, because three compiled entries carried adjacent text nodes.
- **A link must survive an edit to a heading.** Every heading that a body link or a book node reaches carries an explicit `{#anchor}` equal to the key it already had, so URLs do not change. The compiler writes them (one heading in the current library); `fmt` adds one when an edit links to a heading without one. The key algorithm moved to the schema crate so the client, the compiler, and the tools share it.
- **Defaults are declared once.** `license_refs` is written only when it differs from `corpus.toml`. A feat's prerequisite relations are derived from `prerequisite_feats`; the 174 relations labelled `or` stay stored because the list cannot state a label. `provenance` stays optional and is frozen history for new entries to leave out. `validate_library` still requires provenance, so the step that compiles from the corpus must relax that rule for entries without it.
- **One canonical form, enforced.** `fmt` rewrites every file; `fmt --check` prints the first differing line of each file that `write(read(file))` would change. The reader rejects HTML comments, raw HTML, and carriage returns. TOML files carry no comments, because the tool rewrites them.
- **The format has a version and a migration rule.** The reader refuses an unknown `format` and names `cast-iron-corpus migrate`. A format change ships a migration step and is applied as one mechanical pull request, then `fmt`.
- **Fields and body are not unified yet.** Some values live twice, in the typed fields and in the body stat block or labelled lines. `corpus-check` compares the pairs and fails on every disagreement (0 in corpus `v0.1.2`; print the full list with `--drift-report`). It was a warning only while the freeze data still held disagreements.
- **Contributors need only Rust and a text editor.** `corpus-kit/` is copied into the data repository: a README with one recipe per common edit, one annotated example per entry kind, a workflow, and a pull request template. The `cast-iron-corpus` binary depends on the corpus and schema crates only.
- **Step 1 does not switch the build.** `corpus-export` reads the compiled library and writes the text; the compiled library changes only where the format required it (adjacent text nodes in three entries, one explicit heading anchor). Populating the data repository and pinning it in the build stay in later steps.

## Long category lists open one letter at a time, 2026-11-05

Refs [#100](https://github.com/phynics/cast-iron/issues/100).

- **A kind with more than 200 entries groups by first letter.** The threshold keeps small categories (`class`, `race`, `prestige_class`, `skill`, `trap`) as the plain list they were. Digits and symbols share the `#` group, which sorts last, matching the existing jump bar.
- **The selected letter is route state.** `#/browse/kind/spell?l=F` is shareable and adds a history entry, so Back returns to the letter that was open. A missing, malformed, or absent letter opens the first group. The route helpers are `Route::browse_kind` and `Route::browse_kind_letter`.
- **Only the selected group holds entry links.** Every group still renders its heading and count; the other groups render one link on the whole heading row instead of their rows. That link's accessible name is "B, 142 entries". This keeps the DOM small on a phone while leaving the group counts visible.
- **The jump bar sits directly below the count line.** It comes before the facet lenses, so a phone does not have to scroll past every lens to reach it.
- **Focus lands on the selected heading.** The route frame focuses `<main>` one animation frame after a route change, so the browse view waits one more frame and focuses the group's `<h2 tabindex="-1">`. A bare category URL does not steal focus. An unknown `?l=` value falls back to the first group and replaces the URL with the bare kind route.
- **The jump bar is one scrolling row on phones and wraps on desktop.** Below 48rem it keeps the 44 px targets in a horizontally scrolling row, and the open letter is centred in that row, so the sticky bar stays 48 px tall. Above 48rem it wraps to at most two rows, and the group scroll margin clears both. The letter heading is no longer sticky.

## Platform layer

- **CSP and Trunk's inline script.** Trunk writes its start-up module inline, so a strict `script-src` needs its hash. The `post_build` hook `web/stamp-csp.pl` (registered in `Trunk.toml`) hashes the built inline `<script>` and `<style>` and fills the `__CSP_SCRIPT_HASH__` and `__CSP_STYLE_HASH__` placeholders in the policy. Without the hook the page does not start, so a missing hook shows at once. `trunk serve` injects a live-reload script that this policy blocks; develop against `cargo xtask build-site` output.
- **SRI is off (`no_sri = true`).** Chrome warns on the `integrity` attribute that Trunk puts on the wasm preload, and same-origin files already come from the service worker cache.
- **No JavaScript beyond `sw.js` and the bridge, so no pre-render theme script.** `<html>` gets `data-theme` as the first action of `start()`, from a `localStorage` mirror of the IndexedDB choice. The window before the wasm module loads follows `prefers-color-scheme`. A user whose explicit choice differs from the system can see one background change per cold start.
- **Service worker update policy.** The first install skips waiting and claims the page. Later versions wait until the app posts `{type: "SKIP_WAITING"}`; the app shows "Update ready" and reloads on `controllerchange`. The worker never touches `cast-iron-content-*`.
- **Content caches.** One cache per version, `cast-iron-content-<version>`, keyed by the document-relative `content/<path>` URL. The manifest is stored with the version as `<version>/manifest.json`. `active_library` in IndexedDB is the only signal of "ready"; the boot check confirms that the cache holds every manifest file and sends the user back to the installer if not.
- **Install order.** Scan the cache for verified files (resume), check quota against the bytes still missing plus 5%, download with three workers and three tries per file, verify size and SHA-256 before `cache.put`, store the manifest, re-hash every file, write `active_library` (and clear `pending_install`) in one IndexedDB transaction, and only then delete the other content caches.
- **`Library` is `SendWrapper<Rc<_>>`.** Leptos 0.8 context requires `Send + Sync`; the browser runs one thread, so the wrapper never panics.
- **Hash links and `<base>`.** `<base href>` makes `#/x` resolve against the base. `normalize_location()` removes `index.html` and query strings at boot so that plain `#/...` anchors stay same-document navigations. The skip link is handled in code for the same reason.

## Reference screens

- **Search keeps its state in the route and edits it in place.** Typing replaces the history entry after 80 ms; toggling a filter pushes one, so Back undoes a filter but never a keystroke. `RouteView` does not rebuild `Search` when only the search route changes (a memo maps every search route to one value), and the Reader frame leaves scroll and focus alone for search-to-search changes. `route::replace` now writes the route signal through a thread-local handle: it is called from async tasks, where `use_context` finds nothing and the signal silently stayed stale.
- **Facet filters are tied to the selected kinds.** Facet groups show for the kinds that are selected (spell: school, class, spell level; feat: feat type; creature: type, CR, size; item: category, slot; class: class type). Changing the kinds drops facets that no selected kind offers, so no hidden filter stays active. Values come from `facet_values`, and each chip shows the count for choosing it with every other active filter applied. `SearchIndex` builds per-value document lists once when it decodes the index, and one pass over the query's documents with a per-group failure mask answers every chip. Search caches the facet value lists and the discovery snapshot per selection revision. This is derived from existing metadata: it adds memory only and leaves `INDEX_FORMAT_VERSION` at 1.
- **Search timings are exposed as data attributes** on `.results-region`: `data-search-ms` (the `SearchIndex::search` call only, from `performance.now()`), `data-index-ms` (first index load), and `data-query`. The index loads on the main thread. The original POC measured about 8 ms for its 4 MB index. The schema-2 desktop measurement and its limits are in `docs/status.md`; no real-phone memory result supports partitioning yet.
- **Entries render in one pass.** The POC's longest entry (`classes/cleric`, 420 blocks) builds in 13 ms with the shard cached, 39 ms cold, 60 ms with the CPU throttled 4x, with no long task. Progressive chunking would only add delay and break find-in-page, so there is none. Revisit if a source brings entries 5x larger.
- **Heading ids are the compiler's anchors, unprefixed,** because `Route::Entry` anchors and `scroll_to_anchor` use raw ids. A heading without an anchor gets `sec-<slug>`. A content anchor equal to an app id such as `main` would collide; the compiler's slugs do not produce those today.
- **Body-link reverse lookup is built as an optional index.** The References section lists outgoing body links, one per target. Typed relations have their own inverse index for racial traits, archetypes, and feat dependents. The reverse body-link index now supplies the missing direction; see "Reverse body-link index, 2026-11-05" below. A library built before the index has no `backlinks.json`, and the client treats it as empty.
- **Layout.** Below 48rem the primary nav is a fixed bottom bar with four destinations: Home, Browse, Books, and Settings; at 64rem and wider the entry screen puts References in a sticky side column and Search puts filters in a side panel. The rule `main:has(> .wide, > .search-page, > .entry)` widens only the reference screens; Settings, Legal, and the installer keep the reading measure. Grid and flex parents set `min-width: 0` so that a wide table scrolls inside its own wrapper and never widens the page (without it, mobile Chrome zoomed the whole page out).
- **Bookmarks.** A bookmark whose entry is missing from the library shows its saved title, tagged "not in this library", and keeps all actions except opening it. Deleting a collection asks inline and says that bookmarks stay. Recently viewed entries live in `meta` under `recent` (12 items, id and title, newest first).

## Browser acceptance suite and CI

- **The suite tests the real `dist/`.** `tests/e2e/server.mjs` serves an existing `dist/` at `/cast-iron/`, and `playwright.config.ts` refuses to start without one. It also exposes `/__test/*` hooks (corrupt, stall, abort, slow, or refuse a path; overlay an alternative library; read the request log). The hooks exist on this test server only. Each Playwright worker starts its own server on a free port (the `serverOrigin` worker fixture in `tests/e2e/tests/fixtures.ts`), so hooks never leak between workers and parallel runs on one machine never collide. Local runs use 4 workers (`E2E_WORKERS` changes it); CI keeps 1 worker per shard runner. Run by hand, `npm --prefix tests/e2e run serve` still listens on 4318, and `E2E_PORT` changes it.
- **Most tests start from a pre-installed library.** A `preinstalledProfile` worker fixture installs the library once into a persistent browser profile, waits for service-worker control and `active_library`, then closes the profile. The `installedTest` object copies that profile into a fresh temp directory for each test and opens it with `launchPersistentContext` on the worker's own origin. A copy, not a shared profile, keeps tests independent: service-worker caches, IndexedDB, and local storage all belong to one test. macOS clone copies (`cp -c`) and Linux reflinks keep the copy cheap; other systems fall back to a recursive copy. `installLibrary` first waits for either the reader or the Download button, so it downloads only on a clean profile; under `installedTest` it fails instead, because a copy that lost the browser's site data would otherwise reinstall silently and only get slower. Specs that verify installation, the Download offer, request logs, or cache contents, that seed IndexedDB before installing, or that install an overlay or fixture library keep the default `test` and its clean profile.
- **Offline means two things.** Tests call `context.setOffline(true)` and also make the server drop every connection. Chromium's offline emulation does not cover the browser's own check of `sw.js`, which reached the server in the first run, so the allowed exception is exactly `sw.js`.
- **Update test library.** The test builds version 2 in a temp directory (a copy of the library with `legal.json` changed, hashes and manifest recomputed, version by the compiler's rule) and serves it through the overlay. The client does not derive versions, so any `v...` string would do.
- **Browsers.** Chromium (and a 390 px Pixel 7 project for `mobile.spec.ts`) gate CI. WebKit passes all tests locally on macOS; its project turns Playwright traces and screenshots off, because they inject an inline `<style>` into WebKit pages of persistent contexts and the page CSP refuses it, which would be a false console error. WebKit runs in CI with `continue-on-error` until a CI run shows it stable. Firefox is disabled in CI as recorded below.
- **Compiler determinism is a CI check, not a browser test.** The `content` job compiles twice and compares a hash over all of `generated/`.
- **Pages.** `pages.yml` builds as CI does and deploys with the official Pages actions. The repository must have Pages set to the "GitHub Actions" source, which is a repository setting that no workflow changes.

## Public POC rollout, 2026-11-03

- The public POC uses the OGL for the selected Core Rulebook and Bestiary rules, with Paizo's Community Use Policy for permitted descriptive references. The policy review and its limits are in `docs/research/licensing-audit.md`. This does not authorize artwork, campaign books, or additional sources.
- GitHub Issues is the maintained project contact shown on the legal page and in the README. It provides a public contact route without publishing personal contact details. External navigation occurs only when the user follows the link.
- `python3 scripts/check-publication.py` screens the built library before upload in CI and Pages. It checks hashes, source scope, attribution, OGL references, and a finite list of named setting material. Its generated report records the limits. It is evidence for the selected POC, not a legal classifier or a substitute for reviewing a new source.

## Expanded book coverage and prestige classes

- The expansion uses every available book in the pinned snapshot, rather than fetching a newer or different dataset. Selection is explicit and generated from a reviewed 16-book inventory. Unsupported standalone types remain listed in coverage; many are represented inside the selected parent rules trees. This is broader book coverage, not a claim of every published PF1e book or complete standalone category coverage.
- Prestige classes have a distinct schema kind while retaining `ClassFields` and existing IDs. The content schema is version 2; the new client deliberately reads versions 1 and 2 so an old verified library stays usable during an update. The search format stays unchanged. Technology Guide stores Technomancer as a section, so the reviewed source configuration explicitly classifies that URL as a prestige class.
- Placeholder `PFSRD` source labels inherit the reviewed enclosing publication. Explicit non-placeholder source labels remain intact. The catalog and legal page therefore identify the actual books rather than a generic source bucket.
- Named stories and setting material are omitted before deduplication and rendering. Their locations and reasons are part of coverage. Absent optional equipment fields are treated as absent, rather than rejecting the whole record.
- Abrakarn Viper has both creature statistics and construction-item metadata at one upstream URL. The creature remains canonical and retains the supplemental item fields and both provenance paths. Its public identity is unchanged. Conflicting nested copies remain visible in the validation notes.
- The full-corpus text-preservation test now follows URL-addressed records inside trees and exempts only reported policy removals or typed copies rendered separately. Its independent text extraction decodes HTML entities at text-node boundaries and ignores discretionary soft hyphens, matching what users read.

## Relationships and original book order (schema 3)

Product context: `PRODUCT.md`. Data findings and counts: `docs/research/relationship-data.md`.

- **Three new kinds, all from existing upstream families.** `trait` (298 records, plus the 17 `drawback` records as category `Drawback`; 20 religion traits are omitted for Product Identity), `racial_trait` (342), and `archetype` (221 records, 218 promoted). IDs stay URL-derived, so a nested copy that used to be inline text now has the id its url gives. All 9,112 earlier ids and titles survive, with no kind change. The nested copies are identical to the typed records, so the replacement by an entry link drops no text. Schema 3 is required because older clients cannot read the kinds and fields.
- **Families that stay without a category, on purpose.** `animal_companion` (68; 40 of them are in no selected tree, so they are absent), `mythic_spell` (269, absent; a kind would need a relation to the base spell through `spell_source`), `vehicle`, `settlement`, `haunt`, `resource`, `army`, `kingdom_resource` (all in rules trees). None is in the categories that `PRODUCT.md` asks for. They remain in the coverage report. Add them when a category is asked for, not before.
- **Class text typed as an archetype is not an archetype.** Three APG records under the Antipaladin (`Class Features`, `Class Skills`, `Ex-Antipaladins`) carry the type `class_archetype`. The compiler promotes only records whose url sits below a section that ends in `Archetypes`, reports the rest as unpromoted, and leaves them as text in their class.
- **Relations are held by the source entry.** `Part` (racial trait to race), `Archetype` (archetype to class), `Prerequisite` (feat to feat). The inverse is read from `relations.json`, one sorted array of `[source, kind, target]` edges (1,531 edges, 173,675 bytes, 14,491 gzip), never from the shards. The client must tolerate its absence in libraries of schema 1 and 2.
- **No `SpellListMember` relation.** `SpellFields.levels` is the only source of the class and level of a spell. Edges would copy 8,010 distinct pairs into every reader and could drift from it. `lists.json` is an index of that field (128,922 bytes): spells once in a table, lists as positions. Lists whose class has no class entry stay visible with `class` empty.
- **Parents are found in a fixed order.** For a racial trait: the race record that nests it, then a race record above it in the url, then a race with the url's race name (an APG alternate trait goes to the Core Rulebook race, not to an Advanced Race Guide race of the same name). For an archetype: a class above it in the url, then the class whose title equals the upstream `subtype`. A record with no parent is listed in coverage; none occurs today.
- **Prerequisites keep the text and add names.** `FeatFields.prerequisites` is the upstream wording (the extractor now also reads `description`, where 811 of the 1,002 wordings are). `prerequisite_feats` holds feats that the wording names, matched by exact title. A shared title resolves only inside the dependent feat's book. An either-or list sets the relation label `or`; this is a heuristic, so `prerequisite_feats` means "named", not "required". Numeric requirements and races are counted in coverage but not typed.
- **An excluded url excludes everything below it.** `content-policy.toml` matched exact urls only, so promoting traits to typed records would have let 20 deity-specific traits past a container that the policy removes.
- **The book view has curated chapters and upstream order, and it is not a category list.** `book-order.toml` maps printed chapter titles to url prefixes. Entries nested in a tree keep their place; entries that no tree nests follow `upstream-order.json`, which `scripts/extract-upstream-order.py` takes from the databases' nested sets. The compiler does not open the databases, and the input digest covers only the JSON, so the extracted order is committed and reviewed like `legal-notices.json`. A heading appears in the tree only when it holds a nested entry. The url decides which publication's tree holds an entry; 33 entries differ from their `source`. A chapter that is one rules tree is that tree. Entries that no chapter claims go to coverage as unplaced (0 today).
- **Chapter evidence is recorded per book.** The Core Rulebook's first 15 chapters now match the publisher-hosted contents PDF. Its nested placement and appendix grouping still need work. Other outlines remain drafts based on upstream headings and recollection. `docs/research/book-order-evidence.md` records publisher evidence; `docs/research/aon-book-sections.md` and its generated Legacy menu inventory record website navigation, which does not establish print order.
- **Races carry their group as a tag** (`standard_race`, `core_race`, `featured_race`, `uncommon_race`, `monster_race`), because the 35 monster races from the Bestiaries share the Races category with the 44 player races.
- **The client reads schemas 1, 2, and 3.** The new files are not in the required set, so an old library stays usable. The three files sit in the manifest and are hashed like every other file.

## Reference navigation

- Category browsing and book browsing are separate routes. Categories offer alphabetical lists, facets, spell lists, and feat chains. Book pages render only the curated contents tree, preserving its order and showing source notes and review warnings. They do not substitute category lists when chapter data is missing.
- Relation and spell-list indexes load from the installed cache on demand, once per library. Missing schema-3 files in an older library disable the corresponding panels and offer an update route. Ordinary use has no network fallback.
- Racial traits and archetypes link to their parents, and parent entries show the inverse lists. Feat panels retain prerequisite wording alongside named feat links. An `or` label remains visible; these extracted links are not an eligibility calculator.
- `books.json` carries optional source notes and review questions with serde defaults. These additions preserve compatibility with existing schema-3 readers, so the schema remains 3. Entry pages link back to book position and offer previous/next navigation in the curated order.

## Legacy to canonical alias map, 2026-11-04

- **The totality oracle is frozen.** `sources/canonical/legacy-ids.json` holds the 9,968 identifiers the last PSRD production build published, with kind, title, and source, sorted by id. It is exported once and never regenerated from a later build. `sources/canonical/id-map.toml` pins its `sha256` and count in `[meta]`, so an edit to the oracle is a visible, reviewed change rather than a silent rewrite of what bookmarks may hold.
- **The map has three explicit tables.** `[map]` resolves a legacy id through a native upstream identity (`record = "path#key"`), a derived child identity (`derived = "path#key|<kind>:<slug>"`), or an explicit `target = "ref/..."`. `[shared]` is the only way two legacy ids may name one canonical record, and each row needs a note. `[retired]` records `rights`, `out_of_scope`, `no_source`, or `unrepresentable`. Exactly one disposition per legacy id; unknown fields, duplicate dispositions, and canonical ids used as legacy keys fail parsing.
- **Generation verifies the gates, it does not repair them.** `cargo xtask data-alias` rebuilds the canonical catalog from the pinned Pf Data inventory (native `ref/<protocol>/<key>`, planned `ref/racial-trait/...` and `ref/affliction/...`, and extracted allowlisted `ref/rule/...`), then fails on an unaccounted legacy id, an identity the pin cannot produce, a target that does not exist, a chain, a merged target that is not declared `[shared]`, or a `[map]` row whose legacy title and source book do not fit the canonical record. Output is sorted by legacy id, has a fixed field order, and ends with a newline, so two runs are byte-identical.
- **A shared slug is not a match.** The semantic fit gate compares the legacy snapshot's `source` against the canonical record's full publication set (folding `PRPG Core Rulebook`, `Pathfinder RPG Bestiary`, and `GameMastery Guide` to their legacy book ids) and its `title` against the canonical title after case, punctuation, and spacing normalization. Ninety-six rows that only shared a slug moved to `[retired]` with the specific note `derived-rule slug coincidence; not a verified match`. One of them, `ultimate-equipment/rules/wondrous-items/chest`, passes the mechanical checks but was retired in review because the legacy page is the chest slot category and the target is the Chest (huge) item's section.
- **Current state is deliberately incomplete.** 94 legacy ids are mapped (1 direct, 93 derived), none are shared, and 9,874 are retired as `no_source`. A `no_source` row means "no canonical derivation or approved carry-over exists yet"; it is not a claim that the Pf corpus lacks a counterpart. The 8,088 direct-match candidates and the racial-trait, affliction, and rule gaps stay explicit rows until a reviewed audit accepts them. Phase 5 may begin on this format, but no release note may say the gap is closed while those rows remain.
- **The generated file joins the manifest in phase 5.** `cargo xtask data-alias` writes `aliases.json` into the current version directory, adds it to `manifest.json`, and recomputes `content_version` with the compiler's deterministic hash rule. An older library has no file and gets an empty map.

## Legacy alias auto-proposal, 2026-11-04

- **The proposal tool shares the gate, not a parallel matcher.** `cargo xtask data-alias-propose` rebuilds the same canonical catalog as `cargo xtask data-alias` and matches every `no_source` row through `alias::title_fit`, the function the gate itself calls. A proposed row therefore cannot pass the proposer and fail generation. The command writes `generated/migration/id-map.proposed.toml` and `generated/migration/alias-proposals.json`; `--apply` rewrites the committed map. A second run finds no `no_source` rows and produces the same bytes.
- **Matching requires kind, source book, and title evidence together.** The legacy kind must equal the canonical kind; the legacy source must appear in the record's publication set; and the titles must be equal after case, punctuation, and spacing normalization, or differ only by a documented spelling. Comma inversion accepts `Dragon, Red` for `Red Dragon` and drops the PSRD `Primal`/`Imperial` dragon-category word. A trailing family/category parenthetical accepts `Olethrodaemon` for `Olethrodaemon (Daemon)` only for creatures, traits, feats, and afflictions. For items, a parenthetical must be a measure or package (`Chain (10 ft.)`, `Ale (gallon)`), or the `weapon`/`armor` slot label selected by the path tie-break; `Lock (average)`, `Tent (large)`, and `Smart Armor (compact form)` are variants, not matches. A slug is never evidence by itself.
- **Tie-breaks are limited and deterministic.** A native record beats its derived duplicate. A racial trait whose parent race is named by the legacy path wins. A `weapon-special-abilities` or `armor-special-abilities` path picks the candidate whose parenthetical or id names that slot. Everything else stays retired with `ambiguous: <candidates>`, and a proposal that would merge onto an existing non-shared `[map]` target is skipped so the 94 already published rows stay byte-identical.
- **The first proposal pass maps 7,658 more ids.** The map moves from 94 mapped (1 direct, 93 derived, 0 shared) and 9,874 `no_source` rows to 7,752 mapped (5,735 direct, 115 derived, 1,902 shared) and 2,216 retired, all `no_source`. Of the 7,658 proposals, 5,756 are `[map]` and 1,902 are `[shared]`; 17 ties remain ambiguous, 2,195 rows have no matching counterpart, and 4 merge onto an existing published target and stay retired. Remaining gaps are dominated by rules (512), items (418), creatures (327), and racial traits (275); the full per-kind breakdown is in `docs/status.md`. This supersedes the earlier "current state is deliberately incomplete" count, not the rule that an unmatched id stays explicit.

## Client id resolution and bookmark migration, 2026-11-04

- **Resolution is one step and catalog-first.** `Library::resolve` checks the active catalog, then one `aliases.json` entry, then the retirement list. It never follows a chain. A library that still publishes a legacy id therefore keeps opening it even if an alias map is present, which makes the alias-capable shell safe before the canonical library ships. `retired` ids report their reason; the stored row keeps its snapshot and is never redirected to a guessed article.
- **The migration marker is the alias-file hash.** `meta["id_migration"].aliases_sha256` records the manifest hash of `aliases.json`, not the content version. The map is append-only, so a new alias can make a previously retired row resolvable; a content-only change must not force a rewrite.
- **The rewrite is one transaction and is idempotent.** Bookmark rows that resolve to one target merge: `added_at` is the minimum, `collection_ids` is the sorted union, `kind` is the target catalog kind when present, otherwise the earliest row's kind with a lexicographic tie-break, and `title_snapshot` is the earliest row's title with a lexicographic tie-break. An existing canonical row at the target joins the group. Recent ids use the same resolution and dedupe, newest first. Retired and unknown rows are untouched.
- **A refused transaction is not fatal.** The library still loads; reads keep resolving old ids, and the next load retries. This differs from `disabled_books`, whose read failure blocks because there is no correct fallback.
- **Verification is fixture-based until the cutover ships.** The real browser test builds a small legacy library and a small canonical library with an alias map, stars a many:1 pair and a retired id, installs the update, and checks merge, marker, second-load idempotence, old-URL replacement, and offline use. The production library still publishes PSRD ids, so no release note may claim the cutover is live.

## Phase 5 review follow-up, 2026-11-04

- **The kind tie-break is the serialized slug, not declaration order.** The merge rule already said "lexicographically smallest kind"; the implementation used `EntryKind`'s derived `Ord`, which follows declaration order (`Spell` before `Feat`). It now compares `kind.slug()`, so `feat` wins over `spell`. The unit test uses that discriminating pair and reverses read order.
- **A star is the set of stored rows that resolve to an id.** Pressed means at least one stored row resolves to the canonical id, not that the exact key exists. Star adds a row only when no row resolves there, and unstar or Remove deletes every resolving row in one transaction. The entry star, the entry bookmark control, Home, and the bookmarks view share `Library::resolves_to`. The bookmarks and Home lists collapse the set to one displayed row per resolved target with the union of collection membership, and an aliased row shows the target's current title. A refused migration therefore cannot make a saved item look absent, resurrect on unstar, or duplicate on star.
- **A refused conversion is disclosed, not just logged.** When IndexedDB refuses the id rewrite, `Library` records the refusal and Settings shows the non-blocking "Saved items will be converted when storage is available." notice. Every read still resolves old ids and the next load retries.
- **A damaged migration marker reads as absent.** An unparseable `meta["id_migration"]` used to fail the migration on every load. It now decodes tolerantly, like the recents read; the idempotent rewrite runs once more and repairs the marker.
- **Catalog membership trusts the sorted catalog.** `catalog_has` no longer falls back to a linear scan after a binary-search miss. A debug assertion states the sorted-unique-id invariant, and a miss is a miss.
- **A retired route shows its reason.** The entry route previously ignored `Resolution::Retired` and fell through to a generic fetch. It now renders the "not in this library" state with the reason category from design 6.2 and never redirects to a guessed article.
- **The alias map is validated for one step.** `AliasIndex::validate` now rejects a target that appears as an old id in either table and an old id that appears in both `entries` and `retired`, matching the rule that its comment already claimed. The client relies on that check before resolving.
- **The cutover fixture must publish a contract-valid catalog.** The fixture's new library listed its three entries in sourcebook order (`ref/rule/direct`, `ref/rule/shared`, `ref/race/trait`), not sorted by id. The client binary-searches the catalog, so both many:1 targets were reported absent: `plan_migration` gates every alias group on `known(target)`, so the shared and derived rows were never grouped, never merged, and never deleted. The 1:1 row migrated only because its id happened to sort into a reachable slot, which made the bug look like a many:1 defect. The fixture now sorts its catalog entries, as the compiler does.
- **An unsorted catalog is corrupt, not a lookup miss.** `Catalog::validate` checks that entries are strictly ascending by id, and `Library::load` rejects a violation as `LibraryError::Corrupt`. A miss stays a miss (no O(n) scan), but a catalog that breaks the invariant now fails loudly instead of silently mis-resolving every id after the first out-of-order row.
- **Search p95 is recorded, not a correctness gate.** A shared CI runner produced a 102 ms p95 for WebKit against a 4.8 ms desktop figure, so a hard 100 ms assertion failed on load, not on engine speed. The test now annotates the measured p95 and max every run and asserts only a 250 ms smoke bound, which still catches an index that failed to load or an engine regression.

## Canonical book index starts page-ordered, 2026-11-05

- **Page attribution is structured evidence, not body text.** The canonical converter now reads each screened record's `‹SOURCE Publication/page›` markers and `source="Publication/page"` directive attributes into `Converted.pages`, keyed by canonical entry id. A record may name several publications; a range or list keeps its first page, and a repeated publication keeps its earliest page. A derived child inherits its host's attribution unless its own extracted lines carry a SOURCE marker. This is additive: no body text, `SCHEMA_VERSION`, or search format changes.
- **One book per publication, ordered by page.** `books::build_canonical` creates a `BookTree` for every publication that has entries. Sibling order is page, then kind slug, then normalized title, then id. A `NestedLink` child stays under its host, so it follows the host even when its own page number is lower. Entries on the same page are not in printed order. An entry in several publications appears in each book, which the client already handles by taking the first place in book order.
- **The canonical index has no curated chapters yet.** `book-order.toml` matches PSRD `pfsrd://` urls, not Pf Data records. Only the Core Rulebook has a verified printed contents page sequence, and mapping one dataset's chapter titles onto another dataset's records would add a second, unreviewed identity step. The canonical index therefore uses one page-ordered list plus an explicit Unpaged section per book. The curated PSRD chapters remain a later refinement, to be mapped only where page evidence supports it.
- **Unpaged and unattributed entries stay visible.** An entry whose source line names a publication but gives no page goes under that book's `Unpaged` chapter and into `BookOrderCoverage.unplaced` with the reason. An entry that names no publication at all is reported there too and cannot enter a book. ## Body-evidence review of carried duplicates, 2026-11-05

- **A carried duplicate is merged only on body evidence.** `cargo xtask data-carry-review` compares every carried entry with every emitted canonical entry of the same kind and normalized title. The score is token-set coverage of the carried body by the candidate body: `text::blocks_text` projects both bodies to text, tokens are lowercased alphanumeric runs longer than one character, and `coverage = |carried ∩ candidate| / |carried|`. Coverage is directional because merging deletes the carried entry: the candidate must contain the carried text. Symmetric Jaccard was measured first and rejected. A canonical page that combines all levels of *summon monster* or every alignment of *protection from good* scores 0.2-0.5 under Jaccard even when it contains the carried article word for word. Coverage also rejects the opposite error: a glossary or chapter page scores low because most of its words have no counterpart in the candidate article.
- **The acceptance rule has three parts.** Merge only when (1) coverage is at least 0.80; (2) the candidate's catalog publication set contains the legacy book, using the alias gate's folding; and (3) the best candidate leads the runner-up by at least 0.10 when more than one qualifies. A narrower lead stays carried as `ambiguous`. Every other carried entry records one reason: `below_threshold`, `book_mismatch`, `ambiguous`, `short_body` (under 8 tokens), `fallback_target` (the row names an unemitted planned target, not a carried target), `candidate_unavailable`, or `no_candidate`.
- **The threshold sits in an empty band of the observed distribution.** The best same-book coverage of the 145 carried ids that have a same-title candidate in the same book is: `0.00-0.05 1`, `0.05-0.10 1`, `0.10-0.15 4`, `0.15-0.20 3`, `0.20-0.25 1`, `0.30-0.35 1`, `0.35-0.40 2`, `0.45-0.50 1`, `0.55-0.60 2`, `0.60-0.65 3`, `0.70-0.75 2`, `0.80-0.85 2`, `0.85-0.90 10`, `0.90-0.95 29`, `0.95-1.00 82`. No entry scores between 0.744 and 0.828, so 0.80 sits inside an empty band. Forty accepted and twenty rejected pairs were read in full. Every accepted pair is the same article. Rejected pairs above the line are the book-mismatch cases (universal monster rules carried from Bestiary 1 but published in Bestiary 3 or 4) and two-item ambiguities (`powder horn`, `gunsmith's kit` in both equipment files). Rejected pairs below the line include another race's same-named trait (`darkvision`, `weapon familiarity`, `skilled`) and chapter or glossary pages the candidate does not cover.
- **The catalog gate reads inherited attribution.** `catalog_from_inventory` now expands a record's `copyof`/`redirect` before reading its `sources`, matching the converter. Without this, 99 correct rows failed the semantic fit gate because the record carries no `sources` of its own. The change only adds publication ids; it cannot make an existing row fail.
- **The review is deterministic and idempotent.** `data-carry-review` writes `generated/migration/carry-review.json` and `id-map.reviewed.toml`, and `--apply` replaces accepted rows in place, preserving the map's append order, comments, and separators. A second run finds no carried row left above the threshold. `reports/carry-review.json` records the pre-apply run with the reviewed map's SHA-256.
- **Current result.** On this tree the PSRD build publishes 2,245 carried entries. 395 have a same-title Pf candidate, producing 681 scored pairs. 120 are merged: 100 become plain `[map]` rows and 20 become `[shared]` rows because two carried ids merge onto the same target. 2,125 stay carried: `no_candidate` 1,822, `below_threshold` 210, `book_mismatch` 49, `fallback_target` 29, `short_body` 12, `ambiguous` 3. The canonical entry count falls by 120, from 29,515 to 29,395.

## Install button, 2026-11-05

- **The header shows Install only when installing is possible.** All three must hold: the app is not running as an installed app, the launch count is 5 or less, and either the browser gave us a `beforeinstallprompt` event or the browser is iOS Safari. A button that does nothing is worse than none. The rule is the pure function `pwa::show_header_install`, with native tests. "Installed" means a `standalone`, `fullscreen` or `minimal-ui` display mode, or `navigator.standalone === true`.
- **A launch is a browser session.** `localStorage` key `cast-iron.launches` holds the count. A `sessionStorage` key `cast-iron.launch-counted` makes the app count once per session, so reloads and route changes do not count. A new tab or a restarted browser does. If either store throws (private mode), the count is unknown and the header button stays hidden; the app does not fail. An unreadable stored value restarts the count at 1. The count is not tied to the library and is not synced anywhere.
- **The browser event is held by `bridge.js`.** Chromium fires `beforeinstallprompt` once and may do so before the WASM app starts. `js/bridge.js` loads first, keeps the event, and tells the app through a `cast-iron:install-change` window event. The event works once, so the bridge clears it when the prompt opens. After the user accepts or dismisses the prompt, Install disappears from the header and Settings falls back to the browser-menu hint, until the browser fires the event again. The page does not try to open the prompt a second time.
- **iOS Safari has no prompt, so the button opens guidance.** `pwa::is_ios_safari` matches iPhone, iPad and iPod user agents, plus a touch-screen Mac (iPadOS 13 and later reports a Mac), and excludes iOS browsers that carry their own marker (Chrome, Firefox, Edge, Opera, Google app). The guidance is a native `<dialog>` opened with `showModal()`: Share, then Add to Home Screen, then Add. Esc and Done close it, and focus returns to the control that opened it. The icons are self-drawn strokes.
- **Settings keeps the option for good.** Under App, Settings shows the same Install action in a browser regardless of the launch count, an "Installed" badge when running as an installed app, or a hint to use the browser menu when neither a prompt nor iOS guidance exists. It does not claim that installing protects stored data; the storage limits in the spec still apply.
- **One header slot.** `views::header_action` renders at most one quiet action in the header, selected from an enum. Install is the only member today. When an app update action joins, it takes priority over Install.

## Canonical legal screen and alias retirements, 2026-11-05

- **Section 15 is the union, and coverage is judged against it.** The canonical `legal.json` carries PSRD's Section 15 notices, every distinct Pf Data notice that matched an in-scope publication (all printings), and both dataset pins. A publication counts as covered when either list matches it. This matters: Pf Data's own notice file omits the Advanced Race Guide, but PSRD's list covers it, so its 659 records stay under the PSRD notice. Only publications with no notice in either list drive exclusion.

Flattening such a link to its visible text (or dropping an unresolvable parent, relation, or feat prerequisite) is the only outcome compatible with both rules: the host has a valid notice and must stay, and the target cannot be redistributed. ## Filter-conditional counts, 2026-11-05

Settles #41 (split from #15). Search and Browse used to show the same active-book totals, so a tile could say "768 spells" while the active filter showed 12. The two views now have separate meanings.

- **Browse and Books counts are library totals, and say so.** Category tiles and category pages are labelled "Entries in your active books", and Books is labelled "Entries in each book, whether or not it is active". - **Counts do not flicker.** The counts change when a result arrives, together with the result list. While a query is debounced or a search is running, the chips keep the previous numbers. Chips keep a fixed minimum count width, and a chip with zero matches stays in place (dimmed) instead of disappearing, so the layout does not move.

## Heading DOM ids and URL anchor keys, 2026-11-05

This replaces the earlier rule that heading ids were the compiler's anchors, unprefixed. That rule let a content anchor such as `main` or `references-heading` collide with an app element, and let two headings with the same text share one id.

- **A heading's KEY is its URL anchor.** It is the compiler anchor when that is non-empty, otherwise `sec-` plus the slug of the heading's plain text. If neither produces text, the heading has no KEY and no id. Existing `?a=` URLs therefore keep working.
- **Duplicate KEYs in one entry are suffixed deterministically.** The first heading in document order keeps the base KEY. Later headings with that KEY get `KEY-2`, `KEY-3`, and so on. A suffix that matches any literal KEY elsewhere in the same body is skipped, so `sec-x`, `sec-x`, and a real anchor `sec-x-2` become `sec-x`, `sec-x-3`, `sec-x-2`.
- **The DOM id is `h-` plus the final KEY.** The prefix keeps content ids away from app ids such as `main` and `references-heading`.
- **`scroll_to_anchor` tries `h-<anchor>` first, then the raw id.** The fallback keeps routes that target app elements working, including `entry-related` and the browse letter groups.
- **App anchors are reserved.** `rich::RESERVED_ANCHOR_KEYS` lists the route anchors that target app elements on an entry page (`entry-related`). `heading_keys` treats them as already taken, so a content heading whose KEY would equal one gets the next free suffix (`entry-related-2`) and `?a=entry-related` can only reach the Related panel. The 2026-11-05 scan of the 29,515-entry canonical library found no such heading, so no existing URL key changed. A new route anchor for an app element must be added to that list.
- **The renderer and article contents share one assignment.** `rich::heading_keys` walks the same document order as the renderer, and `ArticleContents` links to the final KEY. Headings with a KEY are no longer dropped from the contents just because another heading shares their text.

## CI browser shards and early cache saves, 2026-11-05

Refs [#87](https://github.com/phynics/cast-iron/issues/87). The first split (above) did not shorten the run: each browser suite stayed serial on one runner (`workers: 1`), and the WebKit browser cache was never saved.

## Reverse body-link index, 2026-11-05

- **The index is optional and additive, so the schema stays 3.** `pipeline::package` writes `backlinks.json` plus `backlinks/<NN>.json` from the same entries that the shards hold. Both are listed in the manifest, hashed, and covered by `content_version`. A library built before the index has no descriptor and the client treats the index as empty; an older client ignores the extra manifest files. The descriptor carries `BACKLINK_FORMAT` 1, so adding or removing it does not change `SCHEMA_VERSION` or `INDEX_FORMAT_VERSION`. `CoverageReport::backlinks` is serde-defaulted for older `coverage.json` files.
- **Self-links and typed-relation links are dropped.** A link from an entry to itself is not a reference the reader needs while standing on that page. Both counts appear in `coverage.json` and `coverage.md`.

- **Sixteen FNV-1a shards, not a literal id prefix.** The canonical index is 5,172,403 bytes for 134,391 rows over 16,199 targets, 2.29% of the 226,239,516-byte library. That is below the 10% sharding threshold, but reading and parsing the whole file on every entry view is wasteful on mobile. Canonical ids all start with `ref/`, so a literal prefix would not split them; `backlink_shard` hashes the target id with FNV-1a modulo 16 instead. Shards are 344–408 KB, the client keeps four parsed shards in an LRU, and one entry view reads only its bucket. The shard count is in the descriptor, so a later change does not need a client release.
- **The panel groups by publication and caps the preview.** "Referenced by" is in the same sticky side column as References. Rows group by publication title, groups with three or fewer rows open by default, and a group shows its first eight rows with a "Show all N" disclosure. Rows are ordinary links and native `<details>` disclosures, so keyboard and screen-reader use need no script. A missing index, a missing row, or a read error hides the panel and leaves the entry readable.

## Search ties break by product-line tier, 2026-11-05

Closes [#125](https://github.com/phynics/cast-iron/issues/125), split out of [#101](https://github.com/phynics/cast-iron/issues/101). It reuses the `Tier` of the two entries above.

- **Relevance first, then tier, then title and id.** `sort_scored` in `crates/search/src/query.rs` orders by score descending. Only an exactly equal score (`f32::total_cmp` equal) consults the source rank, lower first. The old title and id tie-breaks follow, so the order stays total and deterministic. A spell reprinted in the Core Rulebook and in a Player Companion has identical text, so it scores equal and the Rulebook entry comes first. Entries with different titles that happen to score equal are also ordered by tier now, ahead of the alphabet. Browsing by filters with no query text is a title listing with no relevance; it is unchanged.
- **The rank is plain data that the client passes at load time, not part of the index.** `SearchIndex::set_source_ranks` takes `(source id, u8)` pairs and builds a per-document rank array that is not serialized. `crates/web/src/library.rs` calls it with `book_tier::source_ranks(&catalog.sources)` right after decoding `search.bin`. `crates/search` still has no dependency on `schema` or on `Tier`.
- **One table, no drift.** `Tier::CATEGORIES` stays the only mapping from category to tier. `Tier::search_rank` is derived from the tier's position in `Tier::ALL`: Rulebooks 0, Player Companions 1, Campaign Setting 2, Adventures 3. A native test checks that every entry of the table agrees with the rank and that the ranks increase. The Books page, the Publication filter and search ranking therefore move together when a category changes tier.
- **Other is neutral.** `Tier::Other` (Miscellaneous, an unknown category, no category) takes `NEUTRAL_SOURCE_RANK` (255), the value that search gives a source with no rank. A PSRD library has no `RPG` category, so every source is neutral and the ordering is the title and id order that it had before. An index that never receives ranks behaves the same way.
- **`INDEX_FORMAT_VERSION` stays 1, `SCHEMA_VERSION` stays 3, and the compiler and the corpus are unchanged.** The alternative, a rank written into each `DocMeta`, would be a format change. The client would then reject every installed `search.bin` until the library was replaced, which means search would break for installed libraries. Deriving the rank from the catalog's existing optional `category` field keeps an installed library searchable, with the new order, immediately. A library whose catalog has no categories keeps the old order. The cost is one pass over the documents when the index loads.
- **A multi-source entry ranks by its first indexed source.** The rank is looked up from `DocMeta.source`, which the compiler sets to `source_ids[0]`, the first source in page order. That is the same source the search Publication filter and its counts use, but it is not always the book where the Books page places the entry, because the Books page uses book order. For an entry reprinted across tiers, the two "firsts" can disagree. Ranking by the best tier over all of an entry's sources would need every source id in the index, which is a format change and out of scope here.

## Body-link pass for the canonical library, 2026-11-06

Refs [#20](https://github.com/phynics/cast-iron/issues/20), [#22](https://github.com/phynics/cast-iron/issues/22), [#23](https://github.com/phynics/cast-iron/issues/23), [#25](https://github.com/phynics/cast-iron/issues/25). `scripts/measure-reference-links.py` counts bare italic or bold spans that name a spell or special ability and carry no link. `crates/content-compiler/src/link_pass.rs` links that residue.

- **This is the one-time linking step for the planned curated corpus.** The pass is a pure function, `link_entries(entries, ranks) -> (entries, report)`. It reads no file and keeps no state, so the export tool for the curated corpus can call it once as a bulk edit. Its rule lists are constants in the module, not a data file. A reviewed data file with add and suppress rules was considered and dropped, because the curated corpus will hold the edited text itself.
- **Only the canonical build runs it.** It runs after `settle_references`, on final ids and over carried entries too. The PSRD build does not run it, and `generated/psrd` and its reports are byte-identical to the previous build.
- **Matching is exact on the whole span.** The span is an `Em` or `Strong` that holds only text. The comparison ignores case, collapses whitespace, and straightens a typographic apostrophe. Trailing whitespace and `,;:.!?` inside the span stay outside the link (`*magic circle,*` links `magic circle` and keeps the comma). The link wraps the original characters, so no word changes. Plain text is never linked automatically.
- **Targets are spells and special abilities.** A special ability is a rule entry from the Bestiary 5 universal monster rules (`json/umr.json`), from the Core special-abilities glossary (a fixed list of `rules_combat01.json` records, because those entries have no parent link), or from the carried Universal Monster Rules section. Feats and conditions are out of scope for the automatic rule.
- **Skips.** A span inside an existing link, inside a heading, a paragraph that is only that span (a label), a header cell, or a span that names the entry that holds it is left alone. The report counts each case.
- **Field labels are never linked.** A span followed by a colon (inside the span or right after it), or, for bold only, followed by `yes` or `no` after optional spaces, opens a stat-line field (`**Spell Resistance** yes`, `_Spell Resistance:_ no`, `Constrict: 3d6`). The same test applies to plain curated matches; there the `yes`/`no` word counts only at the start of a text run, so "spell resistance no longer applies" still links. Each skipped span counts under the label skip, and `field_labels` in the report gives the count per term. The colon test also covers italic because spell sub-headers (`_Spell Resistance:_ yes` in Guards and Wards) are italic labels; the `yes`/`no` test does not, because italic prose such as "_spell resistance_ no longer" is a reference.
- **Ambiguity.** For an italic span, a spell wins over a special ability of the same title, because the books set spell names in italic. A bold span gets no such preference: bold is far more often a label. Among the remaining entries a Core Rulebook entry wins; otherwise the entry from the earliest publication, by the reviewed `publication_date` in `sources/canonical/publication-metadata.toml`, wins. `book-order.toml` is not used: it orders chapters inside a book, not books. A tie that remains stays unlinked and the report lists the tied ids; the category of an ambiguous title is the category of the tied entries, not of every entry with the title. After this pass two spells are tied (a carried copy and a canonical copy of one spell).
- **Blocklist.** `poison`, `fear`, `invisibility`, `resistance` and `web` would resolve to a spell where emphasised text usually names a rule, the concept, or a creature attack. `spells`, `burn`, `rage`, `bleed` and `special abilities` are labels or class-feature names whose only target would be wrong; the measurement showed 2,597, 335, 329, 108 and 22 spans. A reason sits beside each term in the code, and a test keeps the blocklist and the curated list disjoint.
- **Curated terms** link plain text to one fixed entry: `spell resistance`, `spell-like ability` and `spell-like abilities`, `hardness`, `damage reduction`, `darkvision`, `low-light vision`, `fast healing`, `blindsight`, `blindsense`, `tremorsense`, `channel resistance`. A plain match links only at its first occurrence for each target in a block (a paragraph, a list item, a table cell, or a stat row), and not when the block already links that target. An italic or bold span that is exactly a curated term links to the curated target when it names no spell, because the target settles a title with many copies; a span that also names a spell links to the spell (`*darkvision*` in "casts *darkvision*" is the spell). A term skips the target entry and any entry titled like any form of the term, in plain text and in emphasis alike. Plain-text matches that the pass cannot link are counted per term: in a heading, in a label, inside a link, and inside emphasised text. `water breathing` is not curated: the phrase names a Core spell and a Bestiary ability, and the text means the spell in items and the ability in creatures.
- **Report.** `generated/reports/link-pass.json` holds links added per category, hits per rule, blocked terms with counts and reasons, ambiguous titles with their tied ids, per-term counts, and curated targets missing from the input. `coverage.md` carries the same figures in a section.
- **Result on the canonical library.** 21,079 links in 7,409 entries: 11,961 to spells, 8,168 to special abilities, 950 to the Core spell-resistance rule. 5,669 spans over 178 terms were skipped as field labels. 14 emphasised curated spans (7 `spell resistance`, 7 `darkvision`) link to the spell of that name, not to the curated rule. Bare matching spans in the measured scope are 828 for spells (2 in spell bodies; was 12,788 and 398) and 513 for special abilities (was 935); the field labels remain in that residue because they are not references.

## The pinned corpus is the source of truth for the canonical library, 2026-11-06

Refs [#127](https://github.com/phynics/cast-iron/issues/127), [#18](https://github.com/phynics/cast-iron/issues/18). Step 3 of the plan in #127. The format is in `docs/corpus-format.md`.

- **`cargo xtask content` compiles from the corpus.** It reads `phynics/cast-iron-data` through `crates/corpus` (`cast-iron-compile --corpus <dir>`), then runs the stages that derive what the corpus does not store: relations, spell lists, coverage (from the entries, `exclusions.toml`, and `history.toml`), search aliases and facets, backlinks, catalog, search index, and manifest. It reads no upstream dataset and does not need `.cache/sources/psrd-data` or the Pathfinder Data cache.
- **The upstream path stays for one more step.** `cargo xtask content --from-upstream` runs the previous canonical adapter. CI and reviewers use it to prove that the corpus build gives the same bytes. The PSRD build (`--psrd`) is unchanged. A later step removes both upstream paths.
- **The pin is a commit and a tree hash.** `sources/corpus.toml` names the repository, the tag (`v0.1.2`), the commit, and `tree_sha256`: the SHA-256 of one line per regular file, `<sha256 of the file>  <path>\n`, in byte order of the path. `cargo xtask fetch-sources` downloads the archive of the commit, extracts it into a staging directory, and replaces `.cache/sources/cast-iron-data` only when the tree hash matches. `cargo xtask content` re-checks the cached tree before it compiles, so a hand-edited cache fails with the expected and actual hash.
- **Why not the archive hash.** GitHub does not promise that a generated archive stays byte-identical, and the gzip bytes already differ between the tag URL and the commit URL of the same tree. The tree hash covers the files, which is what the build reads. A symbolic link or other special file in the archive is an error.
- **To bump the pin:** tag the new corpus in `cast-iron-data`, set `tag` and `commit` in `sources/corpus.toml`, extract the archive of that commit, set `tree_sha256` to `cargo xtask corpus-tree-hash <extracted dir>`, then run `cargo xtask fetch-sources` and `cargo xtask content`.
- **Provenance is optional.** `validate_library` no longer requires a `provenance` row, because a new hand-written entry has none. The serialized shape does not change: `provenance` stays a required array in `RuleEntry`, and an entry without provenance writes `[]`. A client that reads the old library reads the new one, so `SCHEMA_VERSION` stays. The entry page hides the Provenance section when the list is empty.
- **Reports differ, content does not.** The corpus build has no upstream survey, deduplication counts, or link-pass report, so `generated/reports/validation.json` and `coverage.md` carry a single corpus note instead, and no `link-pass.json` is written. Everything under `generated/content/` is byte-identical to the upstream build.

## Feat fields describe the normal feat, 2026-11-06

Refs [#180](https://github.com/phynics/cast-iron/issues/180). The checker is `crates/corpus/src/drift.rs`.

- **A base feat's `[fields]` are compared only with the body before its first source subsection.** A source subsection is a level-3 heading followed by its own `**Sources:**` line: a `### Mythic …` block, `### Stamina`, an Elephant-in-the-Room replacement, or any other book's version of the same feat. The fields describe the normal feat, so a field that matches only the subsection's `**Benefit:**` or `**Prerequisites:**` line is drift. A `###` heading that organizes the feat's own text and carries no `**Sources:**` line stays in the comparison, so its `**Benefit:**` line still counts as a variant statement of the normal feat.
- **The multiple-statement rule stays inside the normal part.** When the normal part states a label more than once (a variant statement), the field agrees with any of those statements. Subsections are never candidates.
- **Footnote markers do not decide a comparison.** The field writes `[^P]` or `[^X]`, the body carries `^1^` or the flattened `ranks.1`, and neither is rule text. The checker drops the markers and the footnote superscripts before it compares.
- **Measurement on corpus `v0.1.0`.** The previous checker reported 4 disagreements, all footnote-only (`conceal-scent`, `heightened-trap-sense`, `improved-day-job`, `religious-pilgrim`). The stricter checker reports 272 disagreements across 160 feats: 198 in base fields that hold a mythic subsection's wording, 74 that hold the Elephant-in-the-Room tail's wording, and none that hold plain Stamina wording; by field, 140 `benefit`, 120 `prerequisites`, 10 `special`, and 2 `normal`. A field is attributed to the source block that actually states the matched text, not to the nearest `###` heading: 44 of the Elephant-in-the-Room rows sit under a `### Mythic …` heading whose subsection ends with a bare `**Sources:** The Elephant in the Room…` line. The companion change in `phynics/cast-iron-data` (#3) corrects every one and brings the report to 0.
- **A field with no statement in the normal part is drift.** Some fields exist only because another block states them. `text_pair` returned nothing when the normal part had no `**Label:**` line, so nothing compared them and no warning appeared. When the label is stated elsewhere in the body (a source subsection), the field now counts as drift too, with a message that names the missing label. That is an error, like every other drift. A body that never uses the bold label — the carried heading-and-statline entries — stays outside this check, as it was before.
- **A statement inside a quote counts.** A sidebar or variant list may carry a `**Normal:**` or `**Special:**` line inside a blockquote; it is still a statement of the normal feat, so the checker reads quoted paragraphs too.
## Search is a header icon that opens Quick search, 2026-11-06

Refs [#164](https://github.com/phynics/cast-iron/issues/164), [#151](https://github.com/phynics/cast-iron/issues/151). Owner decision from the 2026-11-06 browser review. It revisits the PRODUCT.md line "Search is available as a bar rather than a primary tab": search stays at the top and is not a tab, but it is an icon, not a field.

- **One field per screen.** The header holds a 44 by 44 icon button named "Search" and never a field, so it cannot show a stale query (#151). The results page keeps its own field, without a Search button, because results already update while the reader types. Quick search has its own field, so a screen shows at most one: the results page focuses its field when the icon is tapped, and `/` does the same.
- **Quick search is a native modal `<dialog>`.** It is a full-screen layer under 48 rem and a large sheet near the top above it. The browser gives the focus containment, the `dialog` role and the modal backdrop; the app adds `aria-modal`, the label "Quick search", a Tab wrap inside the layer, and focus to the field in the same event that opens it, because a phone shows the keyboard only for a focus inside the gesture. The expand animation runs only under `prefers-reduced-motion: no-preference`.
- **History.** Opening pushes one history entry with a marker state, on the same URL. Cancel, Escape and Back all end in `history.back()` and a `popstate` handler, so they leave the same history and return to the same page, scroll position and focus (the icon, or the control that was focused when `/` opened it). The scroll position is saved at open and restored at close, and focus is restored without scrolling, because Chromium scrolls a sticky header control's natural position into view. Submitting replaces that entry with the destination, so Back from the results goes to the page that was open before the layer, not to a closed layer. A route change that the layer did not make, such as a typed address, closes it without a history step.
- **The field is empty at each opening.** The route is the only holder of the query; the layer is a way to reach a route.
- **Icon on every width.** A field-styled button on wide screens was considered and left out: a second form of the same control would need its own tests and gives a reader nothing the icon and `/` do not.
- **Starter searches** ("fireball", "grapple", "cure light", "dragon") appear in the layer while the field is empty, and still on the empty results page.

## Quick search suggestions and recent searches, 2026-11-06

Refs [#165](https://github.com/phynics/cast-iron/issues/165), [#164](https://github.com/phynics/cast-iron/issues/164). Builds on "Search is a header icon that opens Quick search".

- **Suggestions come from the engine's ranking.** While the field has text, the layer asks the existing search index (through the active-book discovery snapshot) for the best 64 hits, keeps the best hit of each kind and title, and shows the first 8, each with its name and a muted `Kind · Book` line. A last row, "See all results for …", opens the results page. There is no second index. The order is the engine's, with the tie-break below, so the suggestions are the first rows of the results page for the same text except where the engine tied. A reprint of a spell in other books is one suggestion; the entry page lists the other books.
- **Suggestions are the engine's order with a shortest-completion tie-break for near ties.** The engine scores `fireb` as Firebrand (archetype) 522.5, Fireball 518.7, Firebrand (spell) 518.2, Firebrand (feat) 517.5 and Fireball Trap 515.7, so the results page lists Firebrand first. The scores are not equal, only within one percent of each other, so an exact-equality tie-break never fires. For suggestions only, hits within 1% of the best score of a run whose title starts with the typed text are ordered shortest title first, then the engine's order; other hits and other runs keep the engine's order, and a real score gap is never crossed (`firebal` scores Fireball 519.0 against Controlled Fireball 216.3). The results page and `crates/search` are unchanged. So `fireb` suggests Fireball first and `firebrand` suggests Firebrand first, and the first suggestion can differ from the first result where the engine nearly tied. `shortest_completion_first` in `quick_rows.rs` has the native tests; the 1% band is the `NEAR_TIE` constant.
- **The lookup waits for a pause.** It starts 100 ms after the last keystroke, and a newer keystroke cancels it through the same sequence counter that drops stale answers. When the suggestions change, the highlight is cleared, so `aria-activedescendant` never names a missing row and Enter never opens a row the reader did not see.
- **Announcements.** The count of suggestions is announced only while the list is expanded. The header icon carries `aria-haspopup="dialog"` except on the results page, where it only focuses that page's field.
- **Known limits.** If the address changes while the layer is open (a typed address or an external link), the layer closes and its same-URL history entry stays, so one Back press appears to do nothing. Opening the keyboard on a phone as the layer opens relies on focusing inside the tap; that is verified in Chromium at a phone size, not yet on an iOS Safari device.
- **Combobox, not a menu.** The field has `role="combobox"` with `aria-controls`, `aria-expanded` and `aria-activedescendant`; the rows are `role="option"` in a listbox, 44 px high. Focus stays in the field. Down and Up move the highlight (Up from the first row returns to the field), Enter opens the highlighted row or, with none, searches the text. The highlight has an accent rule at the row start as well as a tint.
- **Escape closes the list, then the layer,** but only while the reader has typed text. The recent and starter searches are the content of the empty layer, not a popup, so Escape there closes the layer at once. Down or typing brings a closed list back.
- **Recent searches** are the last 10 submitted queries: Enter in Quick search, "See all results", a recent or starter search, or Enter in the results page's field. Opening an entry from a suggestion does not count. They are normalized (trimmed, single spaces), unique without regard to case, newest first, and stored in the same `meta` store as the recently viewed entries (key `recent_searches`), so they stay on the device, work offline, and nothing is sent anywhere. Each has its own remove button (a normal button after the option, reachable by Tab; Delete on a highlighted recent search does the same), and "Clear" removes all. With none, the starter searches show instead.
- **Rules are native tests.** `recent_searches.rs` tests order, dedupe, cap, case and empty input. `quick_rows.rs` tests the row rules, the reprint collapse, the cap and the highlight movement.

- **The switch stays a sibling.** The Active switch (`.book-activation`) is a separate control to the right of the link, separated by a hairline, 44 px tall. It never sits inside the link, so the two targets do not nest, and toggling it does not navigate.
- **No inline tree and no "Read [book]" link.** The `<details>` per row, `BookTree`, `DirectoryNode` and the `.book-tree*` CSS are deleted. - **Tier groups, group controls and sort links are unchanged.** The e2e coverage of the lazy contents tree moved from the list to the book page.
- **Back restores the scroll position.** Leaving Books for a book page unmounts Books, and every route change used to scroll to the top, so Back landed at the top of a long list. The router now marks each history entry it reaches with a random id in `history.state` (`scrollId`) and keeps the last scroll offset of each id in memory (`route::remember_scroll`, `arrive_at_entry`). Back and Forward to an entry that this session left return to that offset; a new entry, a reload and an anchor link behave as before (top, or the anchor). `route::replace` and the legacy and boot URL rewrites keep the state they replace; Quick search leaves its own entry with `route::replace_as_new_page`, which starts the page clean. The memory keeps the last 100 entries. A chapter toggle writes its chapter into the URL only while the address bar still shows that book: the browser fires `toggle` in a task after the click, and a Back that lands first would otherwise have the late event rewrite the Books entry into the book page (seen in CI). A group that the reader opened by hand starts collapsed again when Books remounts, so the offset is exact only for groups that are open by default.

## Active books and the presets, 2026-11-07

Closes [#156](https://github.com/phynics/cast-iron/issues/156); refs [#157](https://github.com/phynics/cast-iron/issues/157), [#189](https://github.com/phynics/cast-iron/issues/189). The owner chose no bulk control on any group, including a Third party group. Presets are the only bulk action.
- **Active books is a route (`#/books/active`), not local state.** Each change writes `disabled_books` at once through `Library::update_active_books`, so nothing is left half edited, a reload stays on the page, and Settings can link to it later. The Books tab stays highlighted (`in_section`). `Done` goes Back when the `Active books ›` link opened the page (a flag in memory, so Back restores Books' scroll offset) and otherwise replaces the entry with Books. Entering focuses the H1; `Done` returns focus to the link.
- **Preset rules live in Rust** (`crates/web/src/book_presets.rs`, native tests). A preset is a rule over a book's `Tier` and a third-party flag, not a list of ids: Paizo Rulebooks is the Rulebooks tier; Paizo Rulebooks & More adds Player Companions and Campaign Setting; Paizo Everything is every non-third-party book; Everything incl. 3rd party is every book. The page offers a preset only when its set is not empty and differs from an earlier preset's set, so the fourth is hidden while `is_third_party` returns false. **The hook for #189 is `book_presets::is_third_party(&SourceInfo)`.** When the corpus carries a reviewed marker, read it there; the presets, Undo and the first-run default then need no other change. The matching preset is the first offered preset whose set equals the active set, so a hidden duplicate reads as the preset that is shown. Anything else is `Custom`.
- **Undo is the inverse change.** Applying a preset computes the books it really changes (`book_presets::plan`) and writes them once; Undo writes the inverse. Unknown ids in the stored set are untouched, as before. Undo lasts until the next change on the page (a checkbox or another preset) or until the reader leaves it. Applying the preset that already matches does nothing.
- **How a new install differs from an existing one.** The stored choice cannot tell them apart: an absent `disabled_books` means "every book active" for a profile that never wrote it and for a brand-new profile alike. A marker does. `store::activate_library` runs in one transaction; when the profile has no active library yet and no `book_defaults` key, it writes `book_defaults = "seed"` in that transaction. `Library::load` then calls `book_presets::defaults_action`: with the `seed` marker and no stored choice it writes the Paizo Rulebooks set (`disabled_books` and `book_defaults = "done"` in one transaction); with the marker and a stored choice it only writes `done`; with no marker, or `done`, it does nothing. A profile from before this change has an active library and no marker, so it keeps whatever it has, including "every book active" with nothing stored, and a later library update (also `activate_library`, with a previous library) never marks it. A library with no Rulebooks (the retired PSRD carry-over) is never seeded, so a new install of it keeps every book active rather than none. A crash between install and the first load leaves the `seed` marker, so the default is applied on the next load. The one write path of the seed is the same `disabled_books` key; there is no second storage of the choice.
- **Writes queue instead of failing.** `update_active_books` used to refuse a write while another was saving, so every checkbox disabled itself during a save, which drops keyboard focus. A write now waits for the earlier one and computes its set after it, so no control disables itself and two quick toggles both land. The error message for a busy store is gone.
- **The book page has an Active row** (a toggle row, DESIGN.md) in place of the old disabled notice. The book page, like Active books, stays mounted when the selection changes (the shell no longer rebuilds it on each toggle, which would drop focus). Nothing else on the book page changed; that is #155 and #160.
- **The count line on Books** carries the preset name or `Custom`, and is the only Books layout change here besides removing the switches and bulk controls. Home's "No books are active" notice links straight to Active books.
- **E2E.** The `installLibrary` helper records `book_defaults = "done"` before the first download, so a test profile behaves like an existing install (every book active) unless a test passes `freshBooks: true`. That is the only test hook; the app has no setting for it.

## WebKit stops a Cache read on navigation, 2026-11-08

Refs [#121](https://github.com/phynics/cast-iron/issues/121).

- **A stopped Cache API read is a page error in WebKit.** Home warms the search index in the
  background (a `Cache.match` plus `arrayBuffer` of the whole index). When the document is
  reloaded or left while that read is in flight, WebKit stops its context and reports
  `pageerror: Context is stopped` (from `DOMCacheEngine`). No JavaScript handler receives the
  rejection, so the app cannot catch it and the promise cannot be cancelled. Chromium reports
  nothing. Home already marks the end of the read with `.home-page[data-index-ready=true]`, and
  `installLibrary` waited on it before this change; this change only extends that wait to the
  offline recent-searches test. It is a signal from the app, not a timeout or a retry.
- **Recently viewed is one app-wide signal.** The visit is recorded by the entry screen and the
  list is shown by Home. The `recents` signal in `AppCtx` is the single source for both, loaded
  once at startup (`recent::load_into`) and updated after the store write
  (`recent::record`). A Home that reads the store before that write lands renders the row when
  the signal updates, instead of showing an empty "Recently viewed" until a reload. The stored
  list stays the durable source; `merge_stored` keeps a visit that arrived during the startup
  read from being overwritten by that read's older answer.

## Recents writes are serialised, 2026-11-08

Refs [#273](https://github.com/phynics/cast-iron/issues/273), [#269](https://github.com/phynics/cast-iron/pull/269).

- **The store write takes the signal, not a fresh read.** `recent::record` used to read the
  stored list, modify it, and write it back. Two visits in quick succession each read the same
  old list, and the last write dropped the other visit from storage; a clear could likewise be
  undone by a record that started before it. `record` and `clear` now update the shared signal
  first and write that list. The signal already merges visits in memory, so the last write is
  the newest state.
- **At most one write runs.** A small in-flight queue in `recent.rs` marks a running write stale
  when a visit or clear lands during it, and the writer then writes the signal again. A single
  visit still causes one write; a burst coalesces into the next one instead of racing. The queue
  is the durable-copy rule, not a second source of truth.
- **The startup read joins the queue.** `load_into` merges the stored history into the signal.
  It marks a running write stale so that writer takes the merged list, and when the write
  already finished it writes the merged list itself. Either way a write cannot leave the store
  without that history. A clear wins over a read that was already in flight: the clear bumps a
  generation, and `load_into` discards an answer whose read began before that generation, so a
  cleared history is never merged back. This replaces the old read-modify-write guarantee on a
  deep link or reload on an entry URL.
- **Every Home reload in the e2e suite waits for the index read.** `seedHome` now ends with
  `waitHomeIdle`, and every flow that navigates to Home and reloads at once waits before the
  reload: three in `search.spec.ts`, two in `update.spec.ts`, and one each in `shell-update`,
  `offline`, and `mythic`. Leaving Home while the search-index `Cache` read is in flight is the
  uncatchable WebKit `Context is stopped` above.

- **Spell pages load the relation index.** Both the variants row and the mythic section need it, so `needs(EntryKind::Spell)` now loads `relations.json` as well as `lists.json`. The raw graph supplies the add-on edges; eligibility is tested per add-on id, matching the feat page.
- **Mythic spells use the feat section unchanged.** `Related` calls `mythic_panel` for a spell too, so corpus cast-iron-data #30 can pin `ref/spell/<base>/mythic` add-ons without a second rendering path. The pinned v0.1.11 has no spell mythic add-on yet; the native test covers the branch until the pin PR adds the browser test.
- **A typed relation suppresses the backlink row.** The reverse index already drops a body link whose source states any typed relation to the same target, so a variant's `functions like` link does not repeat the base's `Variants` row under `Referenced by`. Feat chains read only `prerequisite` edges, so a `variant` edge never joins a chain.

## The third-party publication marker, 2026-11-08

Refs [#189](https://github.com/phynics/cast-iron/issues/189). App half only: the corpus marks the
books in a follow-up, so the pinned corpus has no flagged publication yet and the browser test
waits for that pin.

- **One optional corpus field.** `publications.toml` accepts `third_party = true`; absent means a
  Paizo book, and the canonical writer omits it when false. The field sits after
  `publication_date` and before `suffix` in the struct order that the reader, writer and
  formatter share.
- **The `corpus-check` rule is the contradiction only.** `third_party = true` beside a copyright
  line that names Paizo, in any case, is rejected. A missing marker is not rejected when the
  copyright omits Paizo: several Paizo books still have a pending Section 15 notice (#34), so
  absence is not evidence of a third-party publisher. The rule can be tightened once every
  notice is settled.
- **No schema bump.** `SourceInfo.third_party` is an optional additive boolean, serialized only
  when true. Schema 4 is unreleased, so the field costs no `SCHEMA_VERSION` change. The compiler
  copies it from `publications.toml` into `catalog.json`, and output stays deterministic.
- **One tier, last.** `Tier::ThirdParty` follows every Paizo tier in `Tier::ALL`, wins over the
  reviewed category, starts collapsed, and is a disclosure in the search Publication filter.
  `book_presets::is_third_party` now reads the flag, so only `Everything incl. 3rd party`
  includes a marked book; the other three presets, the first-run default and Undo follow from the
  same rule.
- **The search rank is the one exception to the tier order.** `Tier::Other` keeps the search
  crate's neutral rank, `u8::MAX`, so a third-party rank after it cannot be expressed. Third
  party uses 4, after `Adventures` and before neutral; the rank only breaks ties between equally
  relevant hits, and every group still lists `Third party` last. A page whose only results are in
  one collapsed tier opens that tier and spends the budget on it (#142), now for third-party
  books as well as adventures, so it never renders a page of closed headings.
- **Grouping follows the marker.** Books and Manage books build their groups from
  `BookListEntry`, which now carries the flag, so a marked book shows under `Third party` even
  when its reviewed category is a Paizo one. The arrival rule below leaves the group collapsed
  and empty until the reader turns a book on.
- **An arrival starts off.** The app stores `known_third_party`, the set of marked books the
  profile has seen. A marked book that is not in that set is added to `disabled_books` on load;
  the first library that carries the marker therefore turns every third-party book off, and a
  later update that adds one does the same. A book the reader turned on stays in the known set,
  so it stays on. The set only grows: a library that drops a marked book does not forget the
  choice, and a later re-add is not an arrival. This is bookkeeping, not a second copy of the
  choice: `disabled_books` remains the only stored selection. The settle runs inside
  `Library::load` before the `Library` handle exists, so `apply_active_plan`'s in-flight guard
  has no concurrent control write to serialise; the comment in `library.rs` records that and the
  two-tab limit.
- **The first marked library shows a notice once.** When the settle turns a marked book off on
  an existing profile (no remembered set, nothing seeded), it queues `third_party_notice =
  "pending"`. Home shows a dismissible notice in the standard `.notice` style, "Third-party books
  are now off by default. Turn them on in Manage books.", links to `#/books/manage`, and retires
  the flag to `"shown"` so a reload does not repeat it. A fresh install is seeded silently and
  never queues it. The browser test waits for a corpus with a marked publication.

## Book groups follow print; dataset splits nest inside, 2026-11-08

Refs [#13](https://github.com/phynics/cast-iron/issues/13). Owner decisions recorded in the issue
on 2026-11-08. The corpus edit is `phynics/cast-iron-data`; this app repository records the rule.

- **Top-level groups are the printed chapters and appendices.** A book's `chapters` list follows
  the printed contents page for title, order, and grouping. A dataset chapter that print does not
  have does not stay at the top level.
- **A dataset split nests inside its printed chapter.** Base Classes and Core Classes stay inside
  Classes (Advanced Player's Guide), Story Feats inside Character Background (Ultimate Campaign),
  Class Archetypes inside Classes (Ultimate Combat), and New Familiars inside Mastering Magic
  (Ultimate Magic). Each keeps its dataset title and its entries.
- **A dataset hub entry opens the first printed section it links to.** Where the dataset has one
  aggregate entry that print splits or renames, the aggregate becomes the opening entry of the
  first printed chapter it links to, and the linked sections follow as its children or as sibling
  chapters. This keeps every entry in the book tree while the printed title governs the
  top-level label: the Core Rulebook Glossary opens Special Abilities, the Bestiary
  Miscellaneous Monster Rules opens Monsters as PCs, the Advanced Race Guide Age, Height & Weight
  opens Age, and Ultimate Magic Updates becomes Appendix.
- **A printed chapter with no entries gets no group.** It is named in
  `docs/research/book-order-evidence.md` instead, so an empty group never suggests the content
  exists. This covers the Core Rulebook's Inspiring Reading and Game Aids, the Advanced Race
  Guide's Spells appendix, the Bestiary's Appendices 3, 7 and 9-12, and the Game Mastery Guide
  Appendix.
- **Nested placement is a separate check.** Matching the top-level groups does not verify the
  sections inside a chapter. Each book's nested placement gets its own issue, Core Rulebook first.

## Adventure series fields stay optional, 2026-11-09

Refs [#159](https://github.com/phynics/cast-iron/issues/159). Owner decisions recorded in the
issue on 2026-11-09. The data lives in `phynics/cast-iron-data`; this repository owns the format,
the checker and the schema.

- **Only three groupings.** Adventure Paths group by path name and volume, Modules are one line
  ordered by publication date, and Pathfinder Society groups by season and scenario. Companion
  and Campaign Setting sub-lines are out of scope until asked for.
- **The fields are optional in `publications.toml`.** A publication without `series_kind` belongs
  to no series. The data comes from a reviewed script that parses the titles and lists every
  Adventure it cannot parse for review, so the corpus never guesses a grouping.
- **The shape is typed per kind.** `series_kind` is `adventure-path`, `module` or `society`.
  An Adventure Path needs `series` and a positive integer `series_number`; a Module carries no
  other series field; Society needs `season` and, when present, a `<season>-NN` scenario number.
  `corpus-check` rejects the other combinations, and the canonical writer puts the fields after
  `publication_date` and before `third_party`.
- **No `SCHEMA_VERSION` bump.** The fields are additive optional `SourceInfo` members, absent
  from an older catalog, so schema 4 still reads them. The grouping UI is a later change.
